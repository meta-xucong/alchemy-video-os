### 2.2 必须保留的来源行为

1. 来源 `find_string(value, names)`：在每个 dict 上先按 `names` 的顺序检查该 dict 的直接字段值；仅接受 trim 后非空字符串。若没有，按 dict values 的插入顺序递归；list 按元素顺序递归；返回首个命中。
2. 提交 `extract_request_id(result)` 在完整提交 JSON 上使用 `names=("request_id", "id")`；不先裁切 `data`。所以同对象 `request_id` 优先于 `id`；直接字段按 names 次序优先于任意后代；不接受 `task_id`、`taskId`。
   固定来源先以 HTTP 客户端的 `response.is_error` 拒绝 4xx/5xx，然后解析 JSON object 并取来源 ID；它不是一个显式拒绝所有非 2xx 状态的门。目标平台保留自身既有 `200 <= status < 300` adapter gate（因此 3xx 仍按平台现有策略失败），本工作项不改变该平台边界，也不把它描述成来源行为。在 HTTP 2xx JSON object 中，`code >= 400` 或 `status/state` 的失败字样不额外拒绝提交。来源会返回已提取的 request ID。平台必须先持久化这个 ID，之后只能 GET 恢复，不能因为正文字段推测失败而丢弃 ID 并可能重 POST。
3. 查询状态先执行 `response_data(body)`：只有 `body.data` 是 dict 时才选它，否则选 body。选定节点后，以 `names=("status", "state")` 用同一递归首匹配规则取字符串，再小写。不能在选中的 data 对象内未命中时回退读取外层 body。
4. 成功终态精确为 `completed`、`complete`、`succeeded`、`success`、`done`；失败终态精确为 `failed`、`error`、`cancelled`、`canceled`、`rejected`。
5. 固定来源把没有可用状态字符串的查询归为 `unknown`。成功/失败集合之外的所有状态（包括 `unknown` 和任意未知状态字符串）继续轮询；进度字段不参与判断。平台映射为已有 `PROCESSING` 只表示非终态等待，不表示任务成功。
6. 非 JSON 或非对象响应仍属于平台结构错误；提交响应找不到来源支持的非空 ID 仍须 `PROVIDER_PROTOCOL_INVALID`。固定来源通过 `response.is_error` 拒绝 HTTP 4xx/5xx；目标平台另外保留其当前严格 2xx adapter gate，3xx 因此按既有平台策略失败。故此处的“缺状态→unknown”只适用于已通过平台 HTTP 检查且解析为 JSON object 的状态查询响应。它只转为非终态 `PROCESSING`，由现有有限 poll/recovery budget 继续查询；到达既有上限必须按当前 worker 的 pending/failure 终态/恢复策略收敛，禁止无界轮询和重复 POST。本工作项不改变这些边界。

### 2.3 与项目契约的冲突裁定

现行 `AI企业内容生产平台_SUB2API视频能力认证与测试夹具规范.md` 的 `CONTRACT-007` 把“无状态”列为结构错误。该规则与固定来源对有效 JSON 对象“无状态→unknown→继续轮询”不一致。用户已明确要求新设定与原仓库冲突时以原仓库为准；因此实施写集必须先把 `CONTRACT-007` 精确修订为：非 JSON/非对象、提交缺来源 ID、平台现有严格 2xx gate 拒绝的响应、以及无效下载 metadata 仍按既有错误处理；成功 HTTP 响应里的错误码/失败 status 不在 submit 阶段单独拒绝，仍先保存来源 ID；查询 JSON object 缺少可用状态字段按来源作为非终态 `PROCESSING`；绝不推导成功、绝不重新提交。前一做法可能让含业务错误字段的 2xx 提交进入一次查询；这是来源语义，不得暗改。如经独立认证发现实际 profile 必须按正文拒绝，须另起来源证据、契约与审计任务。

与 `AGENTS.md §8.1`“未知响应结构必须 `PROVIDER_PROTOCOL_INVALID`”的边界裁定：本 TaskSpec 将**已通过平台 HTTP gate 且已解析为 JSON object 的查询响应，即使递归搜索不到 `status/state`**，视为固定来源明确规定的 `unknown` 非终态，而不是格式损坏或非对象的“未知响应结构”；用既有 `ProviderStatus.PROCESSING` 表达等待，不新增状态、不推导成功，并只在既有有限 poll/recovery budget 内查询。非 JSON、JSON 非 object、HTTP 被平台 gate 拒绝、submit 缺 ID 仍按 AGENTS §8.1 fail-closed 为协议/Provider 错误。这是 §8.1 中“未知结构”的明确窄解释，不是静默改写：所给 AGENTS 同一规则集§2.2又要求每一步以固定来源优先，且本任务最新明确要求“当新设定与原仓库冲突时，以原仓库为准”；来源直接定义缺状态为 `unknown` 并继续有界轮询，因此来源特例优先于通用未知结构拒绝条款。该窄特例只复用既有 `PROCESSING`、不改变公开 API/DB/持久化状态枚举/事件/Provider wire，无需新 ADR。若实现需扩大到其他对象缺字段、增加新状态或改变持久化语义，立即停止并重新做契约/ADR 审计。

这是内部 Provider adapter 语义，不修改公开 API、数据库、事件、状态枚举、Provider wire 或 C06 的已提交任务不重提规则。若文档审计认为该变更属于需 ADR 的公开/持久化状态语义，须停止本 TaskSpec、先补 ADR；不得先改代码。

## 3. 目标差异与最小目标行为

目标基线：`packages/provider-video/src/sub2api/adapter.ts` 和 `packages/provider-video/tests/sub2api-adapter.contract.test.ts`。审计已确认目标目前：额外识别 `task_id`/`taskId`；unknown 需要 ID match 与自造 `progress` 门槛才是 PROCESSING；有限层级搜索；同对象 `id` 优先于 `request_id`；冲突 ID/status 报错；缺状态报错；状态正规化除小写外还替换空格/连字符；submit 另以 JSON `code>=400` 或失败 status 提前拒绝，即使 HTTP 已成功且来源 ID 存在。上述与固定来源存在可观察差异。

按来源实现一个小型递归首字符串读取器，复用现有 `asRecord`/字符串验证结构，不复制 MCP 项目或更改 transport：

- submit 在原始 JSON 对象递归读取 `request_id`/`id`，字段优先级、递归顺序与来源一致；不识别 task ID 变体；不增加来源没有的 progress 逻辑。
- submit 对 HTTP 2xx 的合法 JSON 对象只按来源抽取 request ID；不以 JSON `code` 或失败 status 代替 HTTP 错误/状态轮询。ID 找到后必须保留并进入现有提交持久化路径。
- status 对象先应用来源 `data` wrapper 选择，再递归读取 `status`/`state`；只 trim/lowercase，不额外规范空格/连字符；同一响应存在多个候选时按来源首匹配优先级处理，不引入并行冲突协议。
- JSON 对象缺状态、显式 `unknown` 或任意非终态字符串都映射为 `PROCESSING`；成功与失败严格使用 §2.2 的集合。非对象 payload、提交缺 ID 仍为 `PROVIDER_PROTOCOL_INVALID`。
- 保留现有 HTTP 错误归一化、路径、request DTO、download metadata、媒体验证、持久化和 worker polling/backoff/recovery；不修改/放宽轮询预算，不新增无界 retry。
