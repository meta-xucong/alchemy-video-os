## 3. 目标实现契约

### 3.1 视觉实体事实

1. 在规划前读取工作区/项目范围内已有 `CanonicalVisualEntity`，所有查询带 workspace_id/project_id；CanonicalSourceBundle 同时冻结 Brief 中的三个已批准节拍、source asset roles/usage 和既存 entity registry。只接受 source_text 中恰好三行 `G02_APPROVED_BEAT_1:`、`G02_APPROVED_BEAT_2:`、`G02_APPROVED_BEAT_3:`，严格有序、唯一、非空；服务端生成 exact quote/span、brief revision 绑定和 beat hash。缺失/重复/顺序错即 BLOCKED，不从模型、旧 Script 或 TaskSpec 自述猜测。
2. 内部 RawSemanticPlan 的精确实体候选结构为 `entity_candidates[]`：公共字段 `{candidate_key, kind, exact_name, source_evidence_refs[], reference_asset_ids[]}`；`kind=CHARACTER` 只允许 `{role?, description?, appearance?, styling?}`，`SCENE` 只允许 `{location, time?, prompt?, description?, lighting?}`，`PROP` 只允许 `{type?, description?}`。每个生成片段必须含 `source_narrative_beat_sequences[]`、`scene_candidate_key?`、`character_candidate_keys[]`、`prop_candidate_keys[]`。这些序号只引用服务端从 Brief marker 派生的 NarrativeBeat；本 G02 任务中每个片段必须且只能引用一个相邻序号，分别为 1、2、3，不允许单片段承载多个 beat。该约束是本任务对 Huobao 强制节拍切段的映射，不推广为平台通用规则；序号列表不得从生成片段 sequence 推导。候选 key 只用于本次模型输出内关联；Raw 输入不得携带正式 entity/revision/PromptPackage/beat/evidence/hash/provider-position IDs。Source refs 必须精确匹配冻结 bundle 的 source span/decision/reference evidence；asset ids 只能从该 Brief 的 READY source refs 中选择。未知/重复/未用候选、跨段错绑、缺证据或资产 usage 不支持实体的输出均拒绝。

7. 项目已存在同名实体时遵守原仓库去重规则复用；不能把图片 asset_id 冒充实体 ID。
8. 私有身份表 `canonical_visual_entities` 以 `(workspace_id,project_id,entity_kind,normalized_identity)` 唯一约束稳定 entity ID。首建使用以该四列为 target 的 `INSERT ... ON CONFLICT DO NOTHING RETURNING`；插入成功者创建 claim。若该精确 identity-key 冲突导致无返回行，则按同一四列 `SELECT ... FOR UPDATE` 读取唯一既存 claim，验证范围并复用其 entity ID；若找不到 claim，或任何非该 identity-key 的唯一约束/数据完整性冲突，则回滚并 fail-closed，不能吞掉或生成第二 ID。Revision 在 claim 行锁内以唯一 `(workspace_id,project_id,entity_id,revision_number)` 追加；并发不同内容必须依次得到唯一递增 revision，相同内容可复用同 hash revision。固定使用 READ COMMITTED。`canonical_visual_entity_revision_assets` 仅追加 ADD/REVOKE；REVOKE 唯一指向同范围既存 ADD，不能更新/删除，活动集为未撤销 ADD。新 plan/schedule 和尚无 ProviderAttempt 的首次消费均重查 active mapping；已有 Attempt 依既有 provider_request_id 恢复语义，不重提。
9. identity 与 content hash 精确复用源语义：角色/道具 identity 为来源 `normalizeName`；场景 identity 为 `normalizeLocation + exact time`（time=`time || ""`）。不 fuzzy match。实体内容 hash 对以下固定字段数组直接调用既有 `semanticValueHash(fixedArray)`：Character `["CHARACTER",role,description,appearance,styling]`、Scene `["SCENE",prompt,lighting]`、Prop `["PROP",type,description]`。该 helper 内部只执行一次 `SHA-256(canonicalJson(value))`；不得先将数组 canonicalize/序列化为字符串再传入 helper。字段均按下述来源 fallback 补成字符串，因此数组 canonical JSON 与来源要求的 JSON 数组序列化字节一致。更新字段严格是来源 `candidate || existing`；角色 styling 为 `candidate.styling || candidate.description || existing.styling`。首次创建严格是 Character `[role||"",description||"",appearance||"",styling||description||""]`、Scene `[prompt||description||location,lighting||""]`、Prop `[type||"",description||""]`。原样字符串，不 trim/额外 Unicode/case 规范；ID/时间/evidence/asset 不入 hash。相同 hash 复用，不同追加 revision。Identity claim 与并发锁是平台存储适配，不宣称为 Huobao 算法。

#### 3.1.8 逐实体引用投影的冻结结构

单一 0026 migration 必须建立三张私有表：`canonical_visual_entities`（唯一 identity claim）、`canonical_visual_entity_revisions`（append-only 内容版本）、`canonical_visual_entity_revision_assets`（append-only `ADD|REVOKE` 映射证据）。映射 ADD 绑定 `workspace_id/project_id/entity_id/revision_number/asset_id/asset_sha256`、mapping evidence 行 ID（即 `mapping_evidence_id`）、canonical `REFERENCE_ASSET` evidence ID、Brief revision ID、原始 usage 字符串和创建时间；表约束保证资产/实体/Brief 同 workspace/project，且 evidence ID 唯一。REVOKE 行只包含所撤销 ADD evidence ID 及其范围的重复绑定字段；仅当引用的 ADD 存在且范围逐项相等时接受，唯一索引禁止重复撤销。没有 update/delete 路径。

本任务仅接受 `USER_DECLARED_USAGE`：它必须逐字等于同一冻结 Brief revision 的 `source_asset_roles[].usage`，并清晰提到同一实体及该图用途。repository 必须通过现有 `resolveCanonicalReferenceSources` 原样透传 usage 到 CanonicalSourceBundle；`provider_role`、`metadata.visual_analysis.summary` 和模型输出不构成实体映射证据。`DIRECT_IMAGE_OBSERVATION` 无现有受控输入入口，故本 TaskSpec 明确不接受、不自动生成、不依靠测试夹具补证；若 Brief usage 不能证明逐实体关系则 BLOCKED，不直接写 DB/文件绕过。Main 检查 bytes/SHA 只能作为素材内容符合声明的门，不替代冻结 usage。

迁移同时给 `storyboard_shot_specs` 增加现有 schema 对应的 `scene_id`、`character_ids`、`prop_ids`、`reference_anchors` 列；更新内部 `ControlStoryboardShotSpec`/draft、INSERT、loader 与 serializer，使四个既有字段 round-trip。`reference_anchors` 对 G02 新语义规划存 Provider-neutral prompt 中按首次出现顺序去重的精确 `@exact_name`，每项须唯一解析到同 ShotSpec 已绑定的实体 revision 和活动映射；不存 asset/candidate/revision ID，不替代其它三个绑定字段。历史字符串按现状原样读取/写回，不追溯验证；缺列的旧数据返回空数组。所有跨表项目归属在同一事务复核；不得增加或更改公开 DTO/API schema。

每个新建语义 PromptPackage 必须在私有 `referenceMap.semantic_entity_reference_projection` 持久化 `SemanticEntityReferenceProjectionV1`，并把其规范化 SHA-256 纳入现有 PromptPackage 完整性 payload。字段严格为：

```ts
{
  version: 1;
  brief_revision_id: string;
  source_hash: Sha256;
  decision_hash: Sha256;
  segment_id: string;
  prompt_package_id: string;
  bindings: Array<{
    entity_kind: "CHARACTER" | "PROP" | "SCENE";
    entity_id: string;
    entity_revision_id: string;
    exact_name: string;
    asset_id: string;
    asset_sha256: Sha256;
    provider_position: number; // zero-based in this segment's immutable visual_input.references
    mapping_evidence_id: string;
  }>;
}
```

一条 binding 表示一个 entity revision 与一张已批准图片在本段内的精确对应。为匹配现有 Brief role 按 asset_id 声明的能力，本任务冻结本次 Brief revision 内 asset→logical entity 一对一：一张图片不得映射到不同实体；同一实体可有多张独立图片。同一资产若已映射到另一 entity，必须 BLOCKED；mapping ADD/REVOKE 事务先锁定该 Brief revision 行，再读取活动映射并校验，以串行化同 Brief 的并发更改。组合图即使画面含多个对象，也不得用于本次多实体映射；本次只使用单体 jar、单体 box、单体 woman、单一 scene 图片。每条关系都必须有同一冻结 Brief 明确声明的精确 usage；不能从通用 provider_role、文件名、旧 metadata 或模型文本推导。`mapping_evidence_id` 必须解析到未撤销的 ADD 行及同 asset ID/SHA 的 canonical `REFERENCE_ASSET` evidence。泛化“产品参考图/风格图”不合格。候选只来自冻结 source bundle；正式 entity/revision/hash/位置/evidence ID 均由服务端生成，模型不得提供或覆盖。

每个可见角色，以及每个可见、被使用、明显展示或特写的重要道具，都必须在本段 prompt 中有精确 `@exact_name` 来源引用，并绑定一个或多个图像；名称必须按 frozen registry 唯一解析。prompt 显式 `@` 的场景也逐项绑定；未 `@` 的场景遵循来源允许的 nullable scene_id。每段至少一个 anchor 是额外门槛，不能替代实体级要求。绑定按 `(provider_position, entity_kind, entity_id)` 稳定排序；本任务每个 provider position 只允许绑定一个 logical entity，distinct positions 必须恰为 `0..references.length-1`，且每个位置与本段 `visual_input.references[position]` 的 asset ID、SHA-256、position 一致。投影 hash 唯一使用现有 `semanticValueHash(value)=SHA-256(canonicalJson(value))`，canonicalJson 实现不修改；输入为除其自身 hash 外的全部 projection 字段。先生成 PromptPackage ID，再构造投影并算 projection hash，随后将 ID、projection 与 hash 加入新版本 PromptPackage integrity payload 算 package hash。完整性校验接收并逐项核对 PromptPackage ID；旧 package 由旧版 hash 分支验证，不得重算或伪造为新版本。

相同投影、hash 与 §3.1.9 的 beat lineage 一并复制进私有不可变 `TaskRun.input_snapshot`，不进入新的 Public TaskRun DTO 字段或 Provider video wire。`completeCreativePlan` 成功事务创建 entity claim/revision、映射 evidence、ShotSpec、PromptPackage 和成功 outbox；失败时以上成功事实均回滚，但既有 `Brief FAILED + creative_brief.planning_failed` 失败 outbox 允许。排程失败允许现有 `WAITING/FAILED` 诊断态；不得新增 Shot/reference binding/TaskRun/queued outbox。Worker 可记录任务失败/审计证据；不得写 ProviderAttempt 或 submit。排程在 TaskRun/queued outbox 前验证 active mapping、beat/projection、package ID/hash 与最终 ordered `visual_input.references`。Worker 的快速 preflight 不是最终授权点；`TaskRunStore.ensureProviderAttempt` 必须在 `packages/persistence/src/task-run-repository.ts` 的同一数据库事务内，读取并验证不可变 TaskRun snapshot、锁定对应 Brief revision 行、复核当前 active mappings 与 reference IDs/SHA/positions，再创建 `ProviderAttempt(CREATED)`。新增这次事务前置校验不得信任 Worker 单独传入的映射事实。

ADD/REVOKE 与 Attempt 创建通过同一 Brief revision 行锁串行化：若 REVOKE 先提交，新的未提交 Attempt 必须拒绝且 Provider submit=0；若 Attempt 创建事务先提交，该 Attempt 即成为不可撤销的持久化提交意图，之后的 REVOKE 只阻止未来的新 Attempt，不追溯取消它；已有 `provider_request_id` 的 Attempt 继续按既有 GET-only 恢复语义，不重提。该原子门仅授权已经通过完整 TaskRun snapshot 校验的 Attempt，不增加新的 retry 或 Provider 调用。并发两种顺序都必须有 integration test。缺失/不一致一律 fail-closed。ReferenceDelivery 与 SUB2API mapper 次序不变，不改 Provider video wire。

#### 3.1.9 私有 NarrativeBeat 身份及其与 GenerationSegment 的 lineage

本节落实领域/API 契约 §1 与 ADR-0041；用户批准的三个 beat marker 是故事层输入，不等于三次 Provider 调用。服务端在 Semantic Director 请求前解析 marker，创建内部 `SemanticNarrativeBeatLineageV1`：

```ts
{
  version: 1;
  brief_revision_id: string;
  source_hash: Sha256;
  beats: Array<{
    sequence: 1 | 2 | 3;
    span: { start: number; end: number; quote: string };
    exact_quote_sha256: Sha256;
    identity_sha256: Sha256;
  }>;
}
```

`span` 使用既有 `SourceTextSpan` 的 UTF-16 code-unit 起止语义；`quote` 是包含 marker 前缀、不含行结束符的原始完整行。`exact_quote_sha256` 是原始 `quote` UTF-8 bytes 的 SHA-256，不做 trim、Unicode、大小写或换行归一。`identity_sha256 = semanticValueHash({brief_revision_id, sequence, exact_quote_sha256})`，复用既有 `canonicalJson/semanticValueHash`；identity 不接受模型生成。`source_hash` 必须等于现有冻结 Brief source hash。

模型输出的每个 GenerationSegment 仅可返回 `source_narrative_beat_sequences[]`，服务端验证三个序号按源顺序把 1、2、3 无重复/无遗漏地分配一次。领域/API 契约 §1 与 ADR-0041 的平台通用模型不把 NarrativeBeat 数量等同 TaskRun 数量；但本 TaskSpec 的三个批准 beats 映射到 Huobao `storyboard-breaker` 的三个强制节拍边界，每 beat 必须独占一个 GenerationSegment，禁止跨边界合并。段数因此固定为三；段内普通人物/道具/entity 变化、动作/因果/情绪变化、镜头/运镜或子镜头变化均须留在 motion/timing 轴，不得增加 Provider segment。profile 已认证安全时长必须允许三段共同覆盖 30 秒，且各满足 Huobao 8–15 秒和单一物理场景；若需第四段或任何约束无法同时满足则 BLOCKED，不得静默改内容、增加切点、拆段或合并 beats。

Lineage 位置固定且不新增公开 DTO/API/event/Provider video wire 字段：CanonicalSourceBundle 内部只向模型提供已批准 marker 的序号/原文 span；RawSemanticPlan 仅含序号数组；SemanticDirectorDecision 原样保留序号数组；`ScriptBeat.sequence` 对应 NarrativeBeat sequence，`visible_facts` 关联其精确 `SOURCE_TEXT` evidence，既有 `generation_segment_sequence` 用验证后的映射；`StoryboardShotSpec.narrative_beat_sequences` 保存每个 GenerationSegment 所含 beat 序号。PromptPackage 私有 `capabilitySnapshot.semantic_narrative_beat_lineage` 保存该段的完整身份条目并纳入 package integrity hash；私有 TaskRun snapshot 复制该段 lineage/hash。不得把 lineage 写入 Public DTO、新表或 Provider video request。

测试必须覆盖本任务三个 beat 按 Huobao 强制节拍边界形成三段，以及拒绝跨节拍合并；增加负例证明同一物理场景内 entity/道具/动作/镜头/运镜/子镜头数变化不会提升 segment count。还须拒绝模型提供的身份 hash/ID、重复/缺失/乱序 beat 序号、跨 Brief revision/source hash、跨场景合并和不满足 Provider 时长边界的分组。接受或拒绝依据冻结来源节拍边界、用户批准的两个场景切点及能力/时长硬约束；本 G02 任务不得用 ADR-0041 通用 beat/segment 解耦规则覆盖来源强制切段。

### 3.2 分镜和时间轴

1. 三个 NarrativeBeat 必须严格从新 Brief source_text 的 `G02_APPROVED_BEAT_1/2/3:` 原文行提取，并按 §3.1.9 生成稳定身份及逐段 lineage。Raw/Decision 仅传源序号；ScriptBeat/ShotSpec/PromptPackage/TaskRun 私有快照按冻结映射引用身份。领域/API 契约 §1 与 ADR-0041 的通用模型不把 NarrativeBeat 数量等同 TaskRun 数量；但本任务三条批准 beat 对齐 Huobao storyboard-breaker 的强制节拍边界，故每个 beat 必须映射到独立 GenerationSegment，禁止跨边界合并。不得从 segment.sequence 合成 beat 映射，也不得把 timeline 行变成额外 Provider task。
2. 本任务只接受 §1.2 所列第一/第二及第二/第三部分之间的两个用户批准场景切点。三段各自对应一个来源节拍/场景块，均须为 8–15 秒且总和严格等于 Brief 的 30 秒；已登记 profile 的认证安全时长必须允许该三段拓扑。不得用技术拆段或合并节拍绕过不匹配：如果任一段不能同时满足 Huobao 时长和 profile 安全时长，或需第四段才能通过，则 BLOCKED。普通动作/实体/镜头变化留在段内时间轴；不得另造切点，也不规定固定平均时长。
3. 每段包含 2–4 个顺序明确的子镜头，每个 2–6 秒；标记不得漏号、重复、跳号或跨段。
4. Huobao 的 Provider-facing video_prompt 行格式是“起点-终点秒：画面”，连续覆盖整段；来源 `description` 中的 `【镜头N】` 必须映射到 1–2 个连续输出时间行。平台可在 Semantic Director 原始候选行前使用 `【镜头N】` 作为仅供确定性关联校验的内部标注；它不是 Huobao 输出格式，canonicalizer 必须验证映射后剥除该标注，再形成持久化/Provider-facing video_prompt，绝不可让该标注泄漏到 PromptPackage 或 Provider 请求。最终时间行从 0 秒开始、顺序连续、无重叠无空隙、末行恰好结束于该 Provider 段时长；按来源 3 秒粒度，尾行允许按总时长取剩余值。每个子镜头映射 1–2 个连续时间行，组时长 2–6 秒，总覆盖等于段时长。
5. 每个 Provider 段必须至少含一个来自该冻结 Brief 已批准引用集合的引用锚点；这只是最低门槛，不得用任意一张产品图代替具体实体的来源引用。Huobao 的 `@` 语义必须逐项保留：每个可见角色必须在本段 Provider-neutral `video_prompt` 中以精确绑定角色名引用；每个画面中可见、被使用、明显展示或特写的重要道具必须逐项以精确绑定道具名引用；本段明确绑定并在提示词中引用的场景也必须以精确绑定场景名引用。每个此类实体引用都必须可确定性地映射到同一实体 revision ID、该实体对应的冻结 Brief 已批准 reference asset ID，以及实际 Provider reference-image 列表中的对应图像。同一 Brief revision 内一个 asset 只能映射到一个 logical entity；同一 entity 可有多个独立 asset，组合图也不得因视觉上含多个对象而映射到多个实体。每个 provider position 只绑定一个 entity，并与实际 reference-image 列表逐项同序。不得因另一实体已有图像锚点而豁免本实体引用。缺少任一实体的已批准、READY、同项目匹配图片或映射不明确时 fail-closed，不得降级成无图文本生成或拿无关批准图充数。Provider-neutral prompt 保留来源 `@精确名称` 引用语义；既有 Provider adapter 只做现存映射，不增加 Provider wire 字段或改动图片顺序。
6. 规划前/落库前做确定性校验：时间行语法、起止、粒度、连续性、内部镜头标注与来源镜头映射、标注剥除、段/总时长、ID 项目归属、每段至少一个有效已批准引用锚点、每个可见角色/重要道具/被引用场景逐实体引用与 asset/entity/provider-image 三方映射、引用集合、dialogue 为空、段数和顺序。不通过时不得创建 READY Storyboard 或 Provider task。
7. 自动结构校验不能证明镜头语义完全忠实；冻结计划还必须由独立只读审计对照本 TaskSpec 和本轮模型输出，并由 Main 检查每个三节拍与单场景条件。

### 3.3 音频和视频边界

- DeliveryPlan 固定字幕 OFF、MusicPlan OFF、旁白 OFF；不能因 Grok native audio owner 自动加音乐、TTS 或旁白。
- 真实调用前必须从本轮已认证 Grok profile 事实读到 `audio_owner=NATIVE_PROVIDER`；未知/未认证时 BLOCKED。MusicPlan OFF/Narration OFF 表示不由平台后加 BGM/旁白/TTS，不等于 Grok native audio 静音。原生音轨按已认证 profile 及现有 Media Runtime 原样保留/合成，禁止静音、替换、重混或添加新轨。最终保留 ffprobe 音频流/codec/时长证据，并试听检查旁白或明显 BGM；若真实 profile 输出与用户“无旁白、平台 BGM OFF”不能兼容，BLOCKED，不能用后期剪辑规避。
- 首个成功成片必须是本轮新 Brief/Storyboard/DeliveryPlan/ProductionRun；三个已批准 NarrativeBeat 按序各自映射到三个 Huobao 强制切段形成的 GenerationSegment，所有相应 segment 均 ACCEPTED；认证 profile 必须支持该三段/30 秒计划，否则保持 BLOCKED。最终 MP4 可播放且媒体校验为 30 秒/480p；抽帧复核三节拍顺序、第二节拍单一实验室场景中的窗外城市、产品包装收尾；音频 owner 与已认证 profile 一致，无平台新增音轨/旁白/BGM，最终 asset READY。任一证据缺失不算成功；所有条件首次满足后立即停止全部真实 Sonnet/Grok 调用。
- Provider 只经现有 Control API、持久化 ProductionRun、Worker、ProviderAttempt、下载校验和 Media Runtime 合成；每个实际提交需记录 run/attempt/request ID（对用户脱敏）和结果。
- 真实 Provider 请求使用既有用户授权账户和既有计费路径；不读取/打印密钥。所有失败必须记录新证据，不能重复无变化的同一失败请求。
