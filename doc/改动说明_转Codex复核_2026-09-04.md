# 改动说明（转 Codex 复核）

> 日期：2026-09-04。本次改动围绕「让本地全栈在 sub2api 真实通道下稳定运行，并修复 planner 把转场段强制锁死在上一段场景」两个问题。所有代码改动均未 commit，工作区待复核。

## 一、本次改动的两个问题与结论

### 问题 A：sub2api 真实通道下，生产运行反复失败 / 仍走 mock

**症状**：前端点击生成后，老项目（保险AI介绍）产出的仍是 mock 视频；或 seg#2 卡住报「本段制作未完成，可重新提交本段」。

**根因（三层叠加）**：
1. **接线缺失**：Control API `apps/control-api/src/index.ts` 构造 `DrizzleProductionRepository` 时用默认工厂，该工厂（`packages/persistence/src/production-repository.ts`）硬编码 `model:"mock-video-v1"`，无视 `VIDEO_PROVIDER` 环境变量。导致生产流程永远发 mock 任务，而 sub2api worker 按 fail-closed 规则拒绝（`PROVIDER_REJECTED`）。
2. **僵尸 worker**：本机残留了多个 `node --import tsx src/index.ts` 进程（正常只需 control-api + 4 worker）。历次重启未杀干净的旧 mock worker 与新 sub2api worker 监听同一队列，抢消费 grok 任务再用 mock 的 expectedModel 拒掉。
3. **签名 key 不一致**：worker 用 `REFERENCE_DELIVERY_SIGNING_KEY` 给参考图 URL 签名，control-api 用同名 key 验证；但两个重启脚本各自 `head -c 32 /dev/urandom` 随机生成，导致 grok 远程拉参考图时 401，拿不到图就随机生成无关内容（这就是第一次 seg#2 出现「山水空镜」的根因）。

### 问题 B：分镜设计了转场，画面却不转场

**症状**：seg#2 分镜明确「镜头拉远切到墨绿驾驶舱新场景」，但生成画面延续了 seg#1 的卧室场景。

**根因**：`packages/creative-planning/src/index.ts` 的 `shotReferencePolicy` 对有参考图的多段视频，第 2 段起无差别强制 `HANDOFF_FIRST_FRAME`，并把 `scene_lock` 写死为「沿用上一段验收交接帧中的场景」。它不读取分镜的转场叙事意图（`hasExplicitSceneChange` 正则只用于拆段，没用于 referencePolicy）。这是本地 MVP 基线（commit 834c66b）自造的逻辑，不来自任何上游仓库，违反了「只移植原仓库、不自造逻辑」的规则。

## 二、具体代码改动清单

### 1. `apps/control-api/src/production-video-input-snapshot.ts`（新增）
- 作用：给 Control API 提供一个「按 `VIDEO_PROVIDER` 选择生成 profile」的任务快照工厂。
- 复用：镜像 `apps/production-worker/src/video-input-snapshot.ts` 的 `createProductionTaskRunInputSnapshotFactory`，内部复用 `@alchemy-video/provider-video` 的 `createRuntimeVideoInputSnapshot` + `resolveVideoProviderRuntimeProfile`，不自造逻辑。
- mock 分支保持与原 `createDefaultProductionTaskRunInputSnapshot` 完全一致。

### 2. `apps/control-api/src/index.ts`（修改 2 处）
- 新增 import `createControlProductionTaskRunInputSnapshotFactory`。
- `DrizzleProductionRepository` 构造从默认工厂改为注入 `createControlProductionTaskRunInputSnapshotFactory(process.env.VIDEO_PROVIDER, process.env.VIDEO_PROMPT_MAX_UTF8_BYTES)`。
- 效果：生产流程的生成任务 model 跟随 `VIDEO_PROVIDER`（sub2api → `grok-imagine-video-1.5`），与 worker 端一致，消除 mock/sub2api 错配。

### 3. `packages/creative-planning/src/index.ts`（修改 2 处）
- `shotReferencePolicy`：新增第 3 参 `hasExplicitSceneChange`（按段）；当该段 `sourceShotBindings[sequence].sceneId` 与上一段不同，或本段文本含显式转场信号时，转场段返回 `REFERENCE_SET`（不锁上一段场景），延续段仍返回 `HANDOFF_FIRST_FRAME`；首段 `REFERENCE_SET`、无参考图 `TEXT_TRANSITION` 行为零变化。
- `createMotionPlan` 的 `scene_lock`：延续段文案不变（「沿用上一段验收交接帧中的场景」）；转场段（REFERENCE_SET 且 sequence>1）文案改为「转场到本段声明的新场景，仅保持人物身份、服装和道具连续」。
- 依据：Seedance-2.5 `references/long-video.md` 的「continue vs new scene」路由 + continuity locks（转场只保留身份级锁）；huobao 的段落级 `scene_id`；OpenMontage 的显式 transition 概念。
- 一个修正：首版误用全篇级 `hasExplicitSceneChange`（对整段剧本测试）判定每段转场，会误伤延续段；已改为对本段文本 `group.join(" ")` 测试的按段判定。
- 后续收口：沿用 Seedance long-video 的 `extreme push/pull + destination opening` 物理转场事实，补充识别「镜头…拉远甩镜…界面/场景/空间…展开/出现」这一保险样本写法；不新增评分、时长或回退路径，并增加真实样本文案回归断言。

### 4. `packages/creative-planning/tests/deterministic-planner.test.ts`（新增测试）
- 覆盖首段 / 延续段（sceneId 同）/ 转场段（sceneId 异）/ 转场段（本段文本有转场信号）/ 无参考图 五条路径的 referencePolicy + scene_lock 实际输出。
- 防回归用例：全篇含「镜头切换」但第 3 段自身无转场词 → 该段仍判 HANDOFF_FIRST_FRAME，证明按段判定点生效。

### 5. `.env.local`（追加 1 行）
- 追加固定的 `REFERENCE_DELIVERY_SIGNING_KEY=local-ref-<hex>`，使 worker 与 control-api 共用同一签名 key。

### 6. 运维脚本（`tmp/`，非源码，本机运维用）
- `restart-control-api.sh` / `restart-workers-sub2api.sh` / `restart-sub2api.sh` / `start-sub2api.sh`：`REFERENCE_DELIVERY_SIGNING_KEY` 从随机生成改为从 `.env.local` 读取固定值。
- 新增 `restart-workers-mock.sh` / `restart-workers-sub2api.sh`：只重启 4 个 worker（不动 API/Studio）。
- Media Runtime 启动统一注入已安装的受控 `MEDIA_TRANSCRIBER_PYTHON_PATH`（与 `PIPER_PYTHON_PATH` 同一解释器）及本机 Hugging Face 缓存；否则 OpenMontage 的 checked-transcript QC 会在能力探测阶段按规则阻断。
- Sub2API 重启脚本优先读取固定 `REFERENCE_DELIVERY_ORIGIN`，仅在未配置时复用已有临时 Tunnel，避免重启后无意切换到旧临时域名。

## 三、复用边界自查（对照 AGENTS.md）

- **移植优先**：核心修复（planner 转场路由）是对 Seedance-2.5 / huobao / OpenMontage 既有机制的薄适配，非自造。Control API 的 snapshot 工厂镜像 production-worker 的既有工厂。
- **不自造**：未新增正则/阈值/启发式评分/枚举值；转场判定只复用现有 `hasExplicitSceneChange` 正则 + 现有 `sceneId` 字段。
- **fail-closed**：sceneId 缺失时默认延续段（保持现状）；无来源信号时不引入新行为。
- **可追溯**：来源登记写入 `doc/AI企业内容生产平台_第三方来源与复用登记.md`（2026-09-04 条目）；开发文档 `doc/AI企业内容生产平台_转场段不被强制锁上一段场景的planner修复开发文档.md`。

## 五、已知边界 / 待复核点

1. **生产侧硬编码 mock 的彻底性**：`packages/persistence/src/production-repository.ts:1132` 的 `createDefaultProductionTaskRunInputSnapshot` 仍硬编码 mock 作为**默认**工厂。本次是在 Control API 注入 profile-aware 工厂覆盖了它。请复核这个「默认值仍是 mock」是否符合预期（是否应将默认值也改为 profile-aware，或保留 mock 作为显式兜底）。
2. **转场判定的信号完备性**：当前转场判定 = 「sceneId 不同」、既有显式转场词，或上游 `extreme push/pull + destination opening` 的明确文字组合。其它没有来源信号的写法仍默认延续段（fail-closed），不会猜测新场景。
3. **planner 修复需重启 worker 生效**：`creative-planning` 由 workflow-worker 加载，需重启 worker 后才对新规划生效；对已在跑的 run 不追溯。
4. **Media Runtime 转录依赖**：本机受控 venv 已安装 faster-whisper；启动时必须注入同一解释器路径，才能执行原有 checked-transcript QC。
5. **未 commit**：所有源码改动在工作区，未提交，待复核通过后再决定提交。

## 六、建议 Codex 重点复核

- `shotReferencePolicy` 的转场段用 `REFERENCE_SET` 是否语义正确（REFERENCE_SET 编译侧指令是「用参考图锚定人物/服装/产品，不替换为通用环境」，不含上一段尾帧锁——这是否等价于 Seedance 的「new scene → 从 canonical references 重新生成」）。
- 按段判定转场的实现是否遗漏了某种「该转场但没被判出」的情形。
- Control API 注入工厂的做法是否与 production-worker 保持完全一致的口径（两侧是否会再次出现 model 不一致）。
