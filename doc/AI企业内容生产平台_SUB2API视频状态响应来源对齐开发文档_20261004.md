### 2.2 来源语义

1. `find_string(body, names)` 对每个对象先按 `names` 的顺序检查本对象字段；找不到时按对象 values 的插入顺序递归字典/数组，返回第一个非空字符串。
2. `extract_request_id` 按 `("request_id", "id")` 顺序递归查找并返回首个非空字符串；因此同一对象内 `request_id` 优先于 `id`。不识别 `task_id` 或 `taskId`。
3. 状态轮询先用 `response_data` 选取 `data`（仅当其为对象），否则选响应对象；随后 `extract_status` 按 `("status", "state")` 优先级递归查找并小写化。
4. `wait_for_video` 仅把 `completed`、`complete`、`succeeded`、`success`、`done` 视作成功终态；仅把 `failed`、`error`、`cancelled`、`canceled`、`rejected` 视作失败终态。
5. 缺失/非字符串状态被 `find_string` 忽略；没有非空状态时，调用方把它变成 `unknown`。所有非成功、非失败状态（包括 `unknown` 和任意未知字符串）继续轮询直至超时；进度字段不参与状态判断。
6. 固定来源没有 `progress` 阈值、没有 `unknown + 匹配任务 ID` 特例，也没有由进度值决定任务是否仍在处理的分支。

来源工作树当前可能有未提交改动；本任务只以以上固定 commit 的 Git blob 为事实，不以工作树版本覆盖固定来源。

## 3. 当前目标偏差

目标基线：`packages/provider-video/src/sub2api/adapter.ts` 与 `packages/provider-video/tests/sub2api-adapter.contract.test.ts`。当前适配器额外接受 `task_id` / `taskId`，且 unknown 仅在匹配响应 ID 与来源无关的 progress 门限下映射为 `PROCESSING`；其他未知状态报协议错误。此外，目标只读取有限的 root/data/video 层级；同一对象内优先 `id` 而非 `request_id`；遇到互相冲突的 ID/status 会拒绝；缺少状态直接报协议错误。固定来源采用递归首匹配、按 names 顺序选择字段、`data` 对象优先于 root，缺失状态归一为 `unknown` 并继续轮询。上述可观察差异需要在后续修订中逐项裁定，不能只删 task ID/progress 分支后宣称完整来源对齐。

本切片只纠正上述来源语义偏差：

- 请求 ID 的来源字段收敛为 `request_id` / `id`；
- 成功和失败终态集合保持与固定来源一致；
- 任何非成功、非失败终态都映射为平台既有 `PROCESSING`，不读取/判断 `progress`；
- `task_id` / `taskId` 不再作为可接受的请求 ID。若响应仅含这两个字段，提交响应按既有“缺少 ID”路径拒绝。

平台 ProviderPort、请求 wire、URL/path、持久化状态、重试策略、错误码类型、环境配置和真实 Provider capability 均不得改变。该映射只表示“来源仍在等待”，不声称 Provider 已成功。
