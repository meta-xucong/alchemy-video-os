## 3. 精确操作范围

允许：

1. 只读核验目标 PID 的进程名、命令行、工作目录、启动模式和日志身份，确认它是 G02 Workflow Worker；3134 Control API 健康、revision 12 失败且无活跃 workflow/TaskRun/ProductionRun。命令行只用于进程内核验；证据仅记录可执行文件、入口、模式及必要的非敏感参数。不得输出或保存原始完整命令行，疑似凭据参数必须脱敏；若无法在不暴露敏感值的情况下确认入口/模式则停止。
2. 先从目标 PID 的有效环境中只读取 `CREATIVE_PLANNING_QUEUE_NAME`，不得打印其他环境值。必须使用能明确绑定该 PID 的受支持进程检查方式，或一份在启动时记录且之后不可变的逐 PID 配置证据；仅有启动脚本默认值、全栈脚本预期值或当前源码默认值不构成证据。若该变量在 PID 环境中不存在，只有在能证明该 PID 确实加载了当前源码版本时，才可使用该版本源码的默认值；否则 effective queue 未知，立即停止。不能读取 PID 环境时，可用可复核的 BullMQ 运行事实替代：revision 12 的不可变 `creative_brief_revision_id` 必须精确出现在唯一一个队列的死信 job 中；同一 Redis 上该队列恰有一名 consumer，且唯一 Workflow Worker PID 的进程登记必须关联到含 `workflow_worker.ready` 的专属日志；日志给出 worker ID；不得有第二个 Workflow Worker PID 或 consumer；其它候选队列不得出现该 revision 的 job。BullMQ consumer 元数据若不提供 worker ID，记录此限制；上述 revision→死信队列→唯一 consumer→唯一登记 PID→专属 ready 日志链必须一一唯一，否则停止。以该 revision-bound 运行事实确定 effective queue，优先于启动器预期值。把 queue name 与后续查询的队列名逐字绑定。只读核验该确切主队列的 waiting、active、delayed、prioritized、waiting-children、paused、stalled/leased 作业数均为 0；dead-letter queue 中的终态 job 只记录，不删除、不重放。

   **本次授权的单事件只读数据库核验例外（不构成一般数据库访问授权）**：用户于 2026-10-03 明确授权为消除 revision 12 的重投不确定性，对本机 `video_local` 数据库执行只读查询。必须在 `BEGIN READ ONLY` 事务内、以 `ROLLBACK` 结束；只读取已核实的 revision 12 ID 和其唯一 dead-letter `event_id` 对应的 `outbox_events`、`event_consumptions` 状态字段及同 revision 的 `creative_brief.planning_requested` 事件 ID 列表。允许输出的仅为 ID、状态时间/布尔状态、consumer 名称、attempt 数；禁止读取或输出 payload 原文、源文案、密钥、URL、用户资料，禁止任何 INSERT/UPDATE/DELETE/DDL。记录 SQL 形状和结果摘要，不保存连接串。必须证明：该 revision 只有一个 planning_requested event；outbox 已 published；对应 `creative-planning-transition` 消费记录 `deadLetteredAt` 非空、`completedAt` 为空、租约已清除；源码确认 `claimCreativePlanningEvent` 在调用 executor 前对同一 event ID 的 deadLetteredAt 返回 `DUPLICATE`。任一条件不满足则停止；不得通过修改数据来“修好”门禁。
3. 精确证明目标进程身份和加载代码：记录 PID、进程创建时间、可执行文件、经安全筛选的必要启动参数、工作目录、watch/non-watch 模式及其来源；原始完整命令行只可用于内存中的匹配判断，不得输出或持久化，凭据型参数必须脱敏。不得只根据登记 PID 或日志文件名推断。对本任务的 `node --import tsx src/index.ts` 路径，必须在启动前记录该入口及其所有运行时导入源码的冻结 SHA-256/manifest，并证明 PID 创建时间晚于该哈希冻结时间、工作目录与入口一致；启动后再次计算相同哈希并确认未变化。若 worker 以 watch 模式运行，则必须有目标 PID 明确的 reload 事件及 reload 后 ready 记录，并在 reload 前后核对源码 hash；否则不能证明加载版本。若原进程已被证明加载当前细分诊断代码，则不做无意义重启，修正本次“输出日志无法绑定 revision”的证据缺口并停止等待新审计方案。若身份、代码版本或加载模式无法在不暴露凭据的前提下证明，停止。
4. 在停止前计算并记录被审计 canonicalizer 源文件 SHA-256 `87c835ff7b7db1ce4f32b32fe03110e0ba926f1ffb5163034fa8cfd08c714306`，并与当前 97-row manifest 一致；同时记录 `src/index.ts` 及其运行时导入源码的冻结 manifest，作为后续新进程加载身份基准。只停止该 Workflow Worker 的确切 PID，不停止其父级/同级服务。若任一文件 hash 已变化、无法取得目标 PID 的 effective queue、PID 身份无法证明或队列非空则停止。
5. 通过受控启动方式仅启动一个新 Workflow Worker：明确记录 `apps/workflow-worker` 工作目录、`node --import tsx src/index.ts` 入口、启动时间、source manifest/hash、effective queue/dead-letter queue names、worker ID；新进程的 `CREATIVE_PLANNING_QUEUE_NAME` 必须与已核验为空的队列名逐字一致。加载与隔离实例一致的进程配置但绝不打印环境变量值。该入口使用 TypeScript source，不声称使用 `dist` build；启动后再次核对 source manifest/hash 未变化，确认 PID 创建时间晚于冻结时间、PID 唯一、没有同队列第二个 consumer，并读取新的独立日志文件。若操作系统/本地受控工具无法安全读取目标 PID 的所需环境字段或验证启动身份，停止，不以猜测、同目录启动脚本或全栈配置替代。
6. 只读检查新的 `workflow_worker.ready` 记录，确认 provider/model/profile/certification source 与原已批准候选一致；不得把该检查描述成 Codex Hook/agent route provenance。
7. 将隔离运行状态登记中的 Workflow Worker PID/log path 更新为新进程；保留其他服务条目不变。若无法证明只改该记录，则停止并报告。
8. 写入证据记录和本补充方案的审计结论。

## 4. 重启后的规划门禁

本补充本身不授权模型调用。只有本补充经独立审计 PASS、worker 单服务刷新验证通过、G02 source/普通代码审计仍绑定同一 97-row manifest `6e47d8bd1a8f22d56e254aaa2057a84b67aba937e1bd6b82d3beb156a2a0f9bb`，且确认不存在活跃任务后，才可按既有用户授权：

1. 创建 revision 13，逐字段复制 revision 12，不改写 source text、style、资产 ID、角色或 usage；
2. 发起恰好一次 Sonnet v3 规划请求，采用全新幂等键；
3. 只读等待该请求终态，并记录固定诊断码及任务/产物数量；
4. 若仍失败，停止规划和视频调用，按实际细分诊断码另立补充方案并独立审计；不得自动重试、改 usage 或放宽 fail-closed。

规划成功也不自动放行视频。Storyboard、DeliveryPlan、source mapping、profile capability、音频 owner、音轨完整性和真实 Provider 前置门必须全部通过；Grok 最多按既有授权分段尝试，并在第一份符合验收条件的完整视频成功后立即停止。

## 5. 验证与证据

- worker 刷新前：Control API health、正确项目/端口、revision 12 终态、无 active workflow/TaskRun/ProductionRun、确切进程入口与 effective `CREATIVE_PLANNING_QUEUE_NAME`、队列名称逐字绑定且主队列无可执行 job；按本节授权例外完成只读 outbox/消费记录核验。数据库查询必须限制到本机、只读事务和上述事件字段，禁止任何数据写入或敏感字段读取。
- worker 刷新后：唯一新 PID、记录的 source SHA/tsx entrypoint/启动时间、同一隔离配置、`workflow_worker.ready`、无第二个同 queue worker；使用独立新日志以绑定 revision 13 的终态诊断；不提交规划或视频请求作为健康探针。
- 后续规划：记录 revision ID/status、workflow worker diagnostic 的固定字段、是否出现 TaskRun/Storyboard/ProductionRun/ProviderAttempt；禁止保存模型原文或私密素材内容。
- 运行质量、模型路由 provenance、Hook 状态分开记录。`ROUTE_UNVERIFIED / HOOK_UNVERIFIED` 不升级、不伪造。

## 6. 停止条件

出现 PID 身份不明、活动任务、端口/项目不符、队列环境不一致、无法安全复用现有环境、启动 profile 不符、重复 worker、配置秘密意外输出或非预期项目副作用时，立即停止，不发起新规划或视频请求。当前 G02 仍不是 `ACCEPTED`；本方案审计 PASS 仅允许执行窄范围 worker 刷新，不代表运行时或视频验收通过。
