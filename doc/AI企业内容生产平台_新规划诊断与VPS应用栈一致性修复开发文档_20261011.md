# 新规划诊断与 VPS 应用栈一致性修复开发文档

日期：2026-10-11

## 1. 目标与已知事实

目标是让新项目的 Studio 一键生产链具有可诊断、可验证的规划门，并避免 VPS 的 API/Studio 与 Worker 从不同目录/旧镜像启动。

已知事实：

- Studio 已有“开始生成视频”自动路径；其前置语义规划失败会停止后续生产。新鲜规划曾两次报 `CANONICALIZATION_SEGMENT_SUBSHOT_INVALID`，均未创建 ProviderAttempt。
- 失败日志只含外层错误码，没有固定子原因；模型原文按现有隐私策略不留存。不得猜测是哪一条 timeline 条件失败。
- G02 时间轴门和 Semantic Director prompt 已有严格同源约束；不得改接受/拒绝语义、移除来源锚定或自动改写/重试模型输出。
- VPS 只读检查确认应用容器的 Compose working directory 混有 `/opt/alchemy-video` 与旧 release 子目录；现有 `restart-app` 会 force-recreate 应用容器但未显式 `--build`，故旧 Worker 镜像仍可能复用。当前不能证明所有服务来自同一源码快照。
- 现有工作树含 9 项用户既有修改。基线和这些修改必须保留，不得 reset、覆盖或混入无关整理。

## 2. 冻结范围

允许：

1. 仅为既有 G02 时间轴拒绝分支增加有限、固定、无输入内容的诊断 issue codes；保持原外层错误码、校验顺序、放行结果、模型响应不落日志。
2. 为每个可区分的失败分支补固定 fixture 测试，证明既有不合格输入仍被拒绝，日志/evidence 不含 prompt、原始模型文本、source、实体值、asset ID 或密钥。
3. 调整 VPS wrapper 的应用更新路径：对已通过配置检查的完整应用服务集合统一显式 build/recreate；增加只读校验，检查运行中的应用容器均绑定同一 canonical Compose 文件和 working directory。Postgres、Redis、MinIO 不在该操作服务清单内。
4. 同步本开发文档、`infrastructure/vps/README.md` 与 `infrastructure/deploy/README.md` 中的准确限制和验收命令。

禁止：

- 放宽 Schema、时间轴/子镜头/来源/实体/素材/分段/Provider 能力门；改写、补齐、自动重试或静默 fallback 模型输出。
- 调用 Semantic Director、视频 Provider、TTS、Veyra、Pixabay 等外部付费/有副作用服务；触碰线上数据、迁移或重启 VPS。
- 将同目录校验描述为同 Git SHA 证明；没有可验证源码指纹时只能报告“同 Compose 路径、由本次统一 build/recreate”，不能声称代码 SHA 已证明。
- 修改既有 V1/其他章节状态，或将本任务描述为 G02/产品/生产验收通过。

## 3. 实施清单

### 3.1 语义规划拒绝诊断

- 在 `semantic-director-canonicalizer.ts` 将 `validateG02Timeline` 的既有拒绝原因映射到下列固定枚举；原因只描述结构条件，不包含输入值。

| 既有拒绝条件（谓词和顺序不变） | 唯一 issue code | Fixture ID |
| --- | --- | --- |
| 存在 `【镜头…】` 但没有合法正整数 marker | `TIMELINE_MARKER_SYNTAX_INVALID` | `TL-01` |
| marker 行本身没有合法的首个时间 row，或已进入分组后出现不符合时间行格式的行 | `TIMELINE_ROW_SYNTAX_INVALID` | `TL-02`, `TL-03` |
| 必需模式下 timeline row 出现在第一个 marker 前 | `TIMELINE_ROW_WITHOUT_MARKER` | `TL-04` |
| row start 与前一 end 不连续、end 不大于 start 或超出 segment 时长 | `TIMELINE_RANGE_OR_CONTINUITY_INVALID` | `TL-05` |
| 非末行不为 3 秒，或末行不在 1–3 秒范围 | `TIMELINE_ROW_GRANULARITY_INVALID` | `TL-06` |
| 没有 timeline、marker 组数不在 2–4，或覆盖没有恰好结束于 segment 时长 | `TIMELINE_COVERAGE_OR_GROUP_COUNT_INVALID` | `TL-07` |
| marker 编号非连续有序，或组 row 数不在 1–2 | `TIMELINE_GROUP_ORDER_OR_ROW_COUNT_INVALID` | `TL-08` |
| marker 组覆盖跨度不在 2–6 秒 | `TIMELINE_GROUP_DURATION_INVALID` | `TL-09` |
| 时间轴通过规范化后，最终 Provider-facing `visual_decision` 仍含私有 `【镜头` marker | `PROVIDER_INTERNAL_MARKER_REMAINS` | `TL-10` |

`TL-01`–`TL-09` 按 `validateG02Timeline` 当前代码顺序产生。`TL-10` 是后续 Provider-facing 输出边界检查，不是 timeline validator 的分支：只有当前置时间轴检查通过、但规范化后的可交付文本仍含内部 marker 时才触发；若同一输入同时包含较早时间轴错误和 marker 泄漏，先返回对应 `TL-01`–`TL-09`，不会运行后续边界检查。Fixture 使用有效 G02 分组且在时间行正文内嵌 marker，证明 TL-10 可达；冲突 fixture 另加非法时间行，证明更早的 timeline 错误优先。其“前一 marker 组为空”的 legacy guard 在当前循环中不可达：marker-only 行先命中 row-syntax 拒绝；该 guard 保留并映射为同一 `TIMELINE_ROW_SYNTAX_INVALID`，不改变执行顺序。每条路径只产生一个 code，不扫描或累计后续错误。
- 只向 `SemanticDirectorCanonicalizationError.issues` 写 `{code}`；不得附带段号、原始行、实际时长、实体/素材身份或 prompt 片段。
- 两个现有外层拒绝分支分别保留其既有错误码；新增 issue 不改变抛出位置、状态、重试策略或 Provider 可达性。
- 完整 fixture 覆盖每个新原因；有效 timeline 的既有输出必须逐字不变，marker 仍只在通过相同门后被剥除。

### 3.2 VPS 应用栈一致性

- `restart-app` 必须从当前调用目录对应的仓库根目录对 canonical Compose 文件统一 `--build --no-deps --force-recreate` 以下完整应用服务集合：`control-api task-worker workflow-worker production-worker document-worker document-runtime media-runtime control-media-runtime studio-web edge`。明确排除：`postgres redis minio migrate`。
- 新增只读 `verify-app`：核验全部必需应用服务均运行，且 Compose 标签指向同一 `working_dir` 与指定 canonical Compose 文件。由于 Compose 默认将首个 `-f` 文件的父目录作为 project working directory，期望标签值为 `dirname(COMPOSE_PATH)`，不是仓库根目录；失败返回非零并列出缺失/不一致服务名，不打印环境变量或容器敏感配置。
- 更新 README：先 `config`，再对完整应用集合执行统一 build/recreate，最后 `verify-app` 与无 Provider 的 HTTP smoke；严禁 `down`/删卷、混合旧容器、把健康状态等同真实 Provider 或商业计费验收。
- 验证脚本用可控 Docker CLI stub 覆盖统一 build 参数、服务全集、数据服务不在重建集合、working_dir/config_files 错配与缺服务拒绝和无 secret 输出。

## 4. 验收门

1. 语义失败接受集与基线完全相同；所有拒绝仍 fail-closed 且没有任何路径创建视频 ProviderAttempt。
2. 诊断只含已知固定枚举，没有模型/用户输入数据；`service.test.ts` 必须验证 `creative_planning.execution_failed.validation_issue_codes` 可区分且原始响应/source sentinel 不出现在日志中。
3. Studio 前端仍能将规划失败与视频 Provider 失败区分；不把规划失败标成生成中/成功，不绕过规划继续创建视频任务。
4. VPS wrapper 的可控命令测试、POSIX shell 语法、配置检查通过；`verify-app` 对混合旧目录返回失败。
5. 相关 Worker、Studio 测试与 typecheck/build 通过；`git diff --check` 通过。测试结果须区分本地 fixture 与真实 Provider/VPS。
6. 冻结最终 diff 后由非实现者只读复审。独立审计未执行/未通过时不得标记任务 `ACCEPTED`。

## 5. 未由本地实现门关闭的外部门

- 新鲜 Semantic Director 规划能否实际满足现有 G02 contract，需一份新的、用户允许的模型运行；本任务仅提供定位失败分支的安全证据，不用合成 fixture 冒充真实通过。
- VPS 当前运行版本仍需在源码快照固定后执行统一部署、`verify-app`、登录后的前端生成验收。当前只读发现不能等同已部署修复。
- 真实视频生成、计费/积分链、历史 QC、浏览器全流程和商用状态均独立验收；不能因代码或 Compose 检查通过而宣称已关闭。
