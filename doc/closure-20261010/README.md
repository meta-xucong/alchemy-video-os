## 文档与实施顺序

1. [恢复一致性设计](recovery-design.md)：R01 的来源、模型、事务、兼容和回归设计。
2. [依赖处置方案](dependency-plan.md)：R02/R03 的官方证据、兼容性试验和风险登记。
3. [验收及切换方案](acceptance-and-cutover.md)：R04–R07 的测试矩阵、现场前置条件、回滚与证据要求。
4. [实施与审计记录](review-record.md)：逐项实施状态、固定提交、实际测试、失败修复、交叉审计和剩余项。
5. [本地交叉复核与同步交接](local-review-handoff.md)：受保护目录、固定 SHA 拉取流程、复核重点和验收回执要求。

实施前先复审方案；任何新增字段或状态约束先同步《领域模型与 API 事件契约》。实施后先运行定向反例，再运行相关全套与类型检查，独立复审同一源代码指纹，再推送并核验精确提交 CI。后续修订不得继承旧提交的测试结果。

## 交付与验收分层

- **代码交付**：本轮实现、负例回归、独立审计及精确提交 CI 均有证据，远端与云端树一致。
- **本地同步**：记录本地实际路径、分支、SHA、干净/脏状态。仅 clean fast-forward，或用隔离 worktree；不将 Draft 分支合入 main。
- **部署就绪**：R05–R07 及现场门均有真实证据、必要授权与风险处置结论，不能由代码交付自动推出。

所有无法在本轮环境闭环的事项必须明确给出缺少的输入、责任环节、下一步与停止条件。不得以“全部修复”覆盖这些未知项。
