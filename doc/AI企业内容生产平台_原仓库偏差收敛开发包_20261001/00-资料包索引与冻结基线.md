### 4.4 统一的 source/target manifest 生成规格

所有 Source Fidelity、普通 Audit 和代码任务必须使用同一 manifest 规则，禁止仅写“已核对 hash”而不记录清单。

1. **路径清单先冻结**：Source 清单仅含 `02` 对应 SF-ID 明确列出的 source 文件、被引用 source 测试和必要 schema；Target 清单仅含本次 TaskSpec allowlist 中的目标文件/测试/契约。不能用整个 `upstream/` 或整个目标仓库的递归 hash 替代逐项映射。
2. **记录文件状态三层**：每个 Target 路径分别记录 `HEAD` 内容（不存在写 `ABSENT`）、index 内容（不存在写 `ABSENT`）、worktree 内容（不存在写 `ABSENT`）。这样既冻结用户原有 staged/unstaged 内容，也能比较实施后的精确工作树；不得把 dirty target 描述为 clean commit。
3. **文件摘要**：对 Git 管理的 blob 内容使用该仓库 `git rev-parse --show-object-format` 返回的 Git object ID 算法；Source/Target HEAD 通过 `<commit>:<path>` 查询、Target INDEX 通过 `:<path>` 查询、Target WORKTREE 使用 `git hash-object --no-filters -- <path>` 计算（不加 `-w`，不得写入 Git object database）。这比较原始 blob/文件字节，不经换行过滤、解码/重编码、格式化或规范化。不存在项写 `ABSENT`。
4. **清单行格式**：使用 UTF-8、无 BOM、LF 换行，每行严格为 `layer<TAB>state<TAB>repo_id<TAB>object_format<TAB>relative_posix_path<TAB>blob_oid_or_ABSENT`。`layer` 为 `SOURCE` 或 `TARGET`；Target `state` 为 `HEAD`、`INDEX`、`WORKTREE`，Source 固定为 `COMMIT`；`repo_id` 为 source 名称或 `target`；路径分隔符一律 `/`，保留原始大小写。不同仓库分别记录 object format。
5. **排序与清单哈希**：按 `layer`、`state`、`repo_id`、相对 POSIX 路径的 Unicode 小写形式排序；其余相同再按原始路径序排序。行间使用单个 LF，末尾必须一个 LF。对最终 UTF-8 manifest bytes 计算 SHA-256，并同时报告总行数、生成时间 UTC、HEAD/branch/source commits。Git blob OID 用来精确绑定文件内容；最终 manifest hash 才是跨文档比较的 SHA-256。
6. **版本绑定**：manifest 必须与 TaskSpec revision、SF-ID 列表、frozen diff 和审计结论一起记录。路径集合、文件字节或 staged/worktree 状态变化即生成新 manifest；旧 receipt 不可复用。
7. **工具与输出安全**：按上面每类状态使用 `git rev-parse <commit>:<path>`、`git rev-parse :<path>` 和 `git hash-object --no-filters -- <path>`；命令只读且不要加 `-w`。不得把 key、环境变量值、媒体或 `.env*` 纳入清单。生成的清单只写入 TaskSpec 允许的证据文档或任务专属临时目录，不写入上游仓库。
