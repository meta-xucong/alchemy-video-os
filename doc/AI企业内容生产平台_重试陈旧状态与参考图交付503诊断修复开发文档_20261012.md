## 1. 目标与范围

将本轮观察到的两个问题作为同一个有界修复任务：

1. 用户点击“重新生成/重试”后，界面立即进入符合真实阶段的“正在提交重试”状态，不能继续显示上一轮的失败提示；服务端接受重试后，切换为准确的制作阶段。旧请求/旧轮询响应不得覆盖新一轮状态。
2. 查明参考图交付 HEAD 预检收到 HTTP 503 的底层对象存储原因；补充安全、可关联的运行诊断和恰当错误分类，并修复经证据确认的具体配置/实现问题。不得把参考图交付错误伪装成 Provider 故障，也不得为追求成功而放松 fail-closed 校验。

### 非目标

- 不改 Provider 接口、模型、提示词、分段策略、计费算法或成功判定。
- 不绕过参考图的签名、资产/项目绑定、MIME/大小、HEAD/GET 校验，不把 503 当成成功。
- 不因这次诊断自动重试失败 Run、不再发起付费 Provider 请求、不清空任务/素材数据。
- 不顺带重构项目页、轮询、对象存储或错误体系。若确认需要超出下列文件边界的改动，先补充本文件的范围与依据，再实现。

## 2. 现场证据与结论边界

### 2.1 前端陈旧失败状态：已由代码路径确认

- `apps/studio-web/app/pages/projects/[project_id].vue` 的 `generationFeedback` 先依据旧 `production_run.status` 返回 FAILED/BLOCKED，未优先处理本地 retry pending 状态（约 686–710 行）。
- 同文件 `retryGeneration()` 设置 `creationBusy=true` 并清空 `creationError`，但未清空 `productionError`；同时它可能重试失败片段，旧的 `currentProductionProgress` 仍是 FAILED/BLOCKED，直到命令响应/项目刷新/事件到达（约 1346–1365 行）。模板的全局 alert 优先展示 `productionError || creationError || projectError`（约 36 行）。
- 独立片段重试 `retryProductionSegment()` 设置 `productionBusy=true`，但只清 `productionError`，且在结束前没有明确的 pending 状态模型（约 1252–1270 行）。
- `apps/studio-web/app/composables/useCreationProgress.ts` 在任一 `localBusy` 时都显示“AI 正在理解内容”（约 85–108 行）；片段重试也会走此分支，因此显示阶段错误。
- `apps/studio-web/app/components/studio/ProductionProgressPanel.vue` 的摘要、标签、颜色只看旧 `props.progress`（约 60–100 行），不看 `props.busy`。重试请求期间仍可能显示旧“失败/有一段需要处理”。
- 现有 `apps/studio-web/tests/project-flow.test.mjs` 主要是源码结构断言；没有覆盖“旧 FAILED 快照 + 点击重试 + 命令尚未返回/新事件尚未到达”的用户可见行为。

结论：这是前端状态优先级和 pending 状态建模缺口。它会让用户误以为重试没有启动，但**不是**后端本次 Provider/参考图故障的原因，也不能证明后端重试已被接受。

### 2.2 最近一次失败：已确认故障路径，底层原因未完全确认

只读检查目标 VPS，没有执行重试或 Provider 调用。最新记录：

- Production Run：`prd_01M4RB7X`，状态 `BLOCKED`；3 个 segment 均 `FAILED` 且标记 retryable。
- 3 个 segment 关联同一 TaskRun：`tsk_01M4RB7Y`，状态 `FAILED`，错误码 `PROVIDER_UNAVAILABLE`。
- 该 TaskRun 关联 ProviderAttempt 数：0；已保存 Provider request ID 数：0；Usage record 数：0。故本 Run 在证据上没有进入 Provider 提交/扣费阶段。
- Worker 结构化日志在近期窗口多次记录 `task_worker.reference_delivery.preflight_failed`，`reason=HTTP_STATUS`、`http_status=503`、`attempts=3`、`retryable=true`。
- Control API 日志记录 `/provider-input/[redacted]` 的 HEAD 响应为 503，耗时约 2–10ms；没有输出签名 token 或完整路径。
- Control API、Task Worker、MinIO、Edge 容器当时均为 running；Control API/MinIO health 为 healthy，容器 restart count 为 0。此健康信号不能证明对象级 `HeadObject` 可用：Control API healthcheck 只访问 API readiness；MinIO healthcheck 仅检查 liveness。
- Worker 事件没有 TaskRun/ProductionRun 标识，API 日志没有 Worker preflight attempt ID；因此虽时间和故障模式吻合，当前日志不能对每一个 503 进行不可歧义的跨服务关联。
- 过滤后的 MinIO 错误日志中没有可用诊断记录。没有读取/输出密钥、签名 URL、图片内容、Provider 原始响应或用户 prompt。

代码路径：Worker 对签名参考图做 HEAD 预检；API `GET /provider-input/:token` 路由依据方法分支处理 HEAD，并读取已绑定资产的对象元数据。该路径捕获 `StorageUnavailableError` 后返回空 503。对象不存在、签名无效、资产/项目/哈希/MIME/大小绑定不匹配会返回 404，而非 503。结合近期 Worker/API 的状态，**对象存储元数据访问失败是优先调查假设**；现有证据不能确认具体 API 503 属于该 Run，也不能确认实际底层 S3/MinIO 错误。已知事实只支持“Worker reference-delivery HEAD 收到 503 且在 ProviderAttempt 创建前停止”，不支持“视频 Provider 不可用”。

待确认的底层原因仍包括：S3 凭证/权限错误、bucket 初始化或 CORS 初始化失败、对象 HEAD 返回非 NotFound 错误、MinIO 短暂故障、API→MinIO 网络/连接问题、错误地把某类 S3 响应折叠成 `StorageUnavailableError`。目前没有证据在这些候选项中定案。

额外缺口：`apps/control-api/src/app.ts` 在 relay catch 中只返回 503，没有记录 `StorageUnavailableError.diagnostic`。`packages/storage-client/src/index.ts` 的 `storageDiagnostic()` 目前仅检查 SDK 的 `name/code/httpStatusCode` 类型后保留原值；`name/code` 并非安全枚举，也没有长度/字符限制，不能直接作为白名单日志字段。现有 Worker 日志和 API request log 缺少共同的安全 correlation ID，造成无法单次请求闭环。

## 3. 冻结要求与硬约束

- 数据/内容准确性优先：HTTP 503 必须继续 fail closed，不能将未验证的参考图交给 Provider。
- 用户界面必须区分“提交重试中”和“服务端已接受、后台制作中”；只有收到命令成功响应/权威的新状态后才能宣称后台重试已启动。
- 任何旧快照、旧轮询、延迟的 SSE/事件刷新不得覆盖新 attempt 的较新状态。优先使用服务端 attempt/revision；本轮使用 `updated_at` 仅作为临时、带条件的持久化版本：不得使用客户端时钟或响应到达顺序，并且必须确认相关 API 读取同一权威写入源、每次状态变更都推进该字段、时间精度足以区分状态变更。相同时间戳时保留当前值而不推断新旧。任一条件未验证时，该项仍是验收缺口，应改为服务端单调 revision/attempt 序号。
- 对外错误文案须准确：参考素材交付失败不能显示为“视频 Provider 不可用”。用户文案不泄露内部主机、对象 key、凭证、原始 S3 响应。
- 错误分类按可重试性区分：瞬时网络/5xx 可有限重试；权限/配置类错误不可重复盲重试；明确的 404/绑定错误保持拒绝。具体映射必须由实际 SDK 错误码和测试证据驱动，不允许泛化吞错。
- 日志只能记录 allowlist 字段，例如 operation、映射后的安全错误类别、范围约束后的 HTTP status、retry count、request/correlation ID 和任务 ID 的短化/不可逆标识；禁止 token、query string、对象 key、完整 URL、请求头、密钥、图像内容和 Provider 请求体。
- 不新增外部 Provider 调用，不改账单副作用；开发验证使用 mock/local test doubles。

## 4. 实施设计

### 4.1 前端重试状态

涉及文件（默认范围）：

- `apps/studio-web/app/pages/projects/[project_id].vue`
- `apps/studio-web/app/composables/useCreationProgress.ts`
- `apps/studio-web/app/components/studio/ProductionProgressPanel.vue`
- 对应 `apps/studio-web/tests/` 中的行为测试；如需组件测试配置，只允许最小变更。

实现要求：

1. 为“重试请求 pending”建模，至少区分一般任务重试与片段重试；点击后同步清除这次操作所对应的旧 generation/production 错误提示，并立即显示“正在提交重试”，不是“AI 正在理解内容”。
2. 在 API 命令尚未确认前，不显示“已开始生成/后台制作中”；成功响应后转为“重试已受理/正在制作”，并使用响应携带的最新状态。
3. 命令失败时清除 pending，展示本次命令错误；失败响应才允许展示新的失败，不要把先前 Run 的旧 `safe_summary` 继续当作本次结果。
4. 成功提交后，在对应 attempt 有权威更新前，不让旧 FAILED/BLOCKED 快照覆盖 pending/accepted 状态；新 attempt terminal 时再显示该 attempt 的结果。
5. `ProductionProgressPanel` 的 label/tone/summary 与页面级 feedback 使用同一状态优先级，不能一个显示“重试中”、另一个仍显示“失败”。
6. 防止刷新竞态：旧的 project refresh/event response 不得覆盖新 retry command response。优先使用服务端 attempt/revision 或 request ID；可在客户端使用递增本地 intent generation 作防旧响应屏障，但它不能取代服务端 run/attempt 的权威身份。
7. `canRetry`/重复点击保护应继续有效；不改变当前后端重试授权与计费语义。

建议优先级：本次 retry pending/accepted 状态 → 对应 attempt 的权威活动状态 → 对应 attempt 的 terminal 状态 → 旧历史状态。终态全局提示必须带有正确 attempt 关联。

### 4.2 503 诊断与根因修复

涉及文件（先以诊断补强为最小集，根因修复按证据增加）：

- `apps/control-api/src/app.ts`：`providerInputResponse` 的存储异常 catch。
- `apps/control-api/src/middleware/logger.ts` 或现有安全日志工具（仅在必要时）：request/correlation ID 贯穿。
- `apps/task-worker/src/reference-delivery.ts`：preflight 事件增加与本次 task/attempt 关联的 opaque correlation id；禁止记录 URL/token。
- `packages/storage-client/src/index.ts`：仅当现有 `StorageDiagnostic` 不够区分错误类别时，扩展为有限 allowlist，不输出 SDK 对象。
- 相应 Control API、Task Worker、storage-client 的单测/集成测试。

实现顺序：

1. Worker 对每次逻辑 reference-delivery preflight（包含该 preflight 内有限重试与 HEAD/GET fallback）生成一个随机 UUID correlation ID（由 Worker 代码生成，不读取 TaskSpec、用户输入或 query 参数），通过专用 `X-Reference-Delivery-Correlation` header 传递；API 只接受规范 UUID 格式，格式错误/缺失时不信任该值，并始终生成自己的 request ID。API 每个请求完成日志同时记录 API `request_id` 和通过格式校验的 correlation ID；Worker 终态失败日志记录同一个 correlation ID、task/attempt 的安全短标识和 HTTP 状态。不得把 correlation ID 放进 URL。token path 必须继续固定 redact。
2. API 捕获 `StorageUnavailableError` 时记录安全结构化诊断：`operation=provider_input_metadata_head`、correlation ID、映射后的错误类别枚举、范围约束后的 HTTP status、storage stage（bucket init / object metadata head）、HTTP 方法和最终状态。不要把 SDK 的原始 `name/code/message` 或诊断对象直接写日志；需要细分时，在 storage-client 把 SDK 字段映射到固定、有限、安全类别，对未知/超长/含控制字符输入统一映射 `UNKNOWN_STORAGE_ERROR`。任何对象 key、bucket secret、token/URL 均不记录。
3. 对真实 S3/MinIO 错误做最小复现，确认根因后才选择最小修复：
   - 权限/凭证：修正部署配置/最小桶权限；确认后对 `AccessDenied` 及时失败，不重复三次。
   - bucket 初始化/CORS：区分初始化状态和对象检查；CORS 非必要时不得阻断服务器端 HEAD（需先审计上传浏览器流程和现有启动契约，避免扩大变更）。
   - 网络/瞬时 5xx：修正连接/超时/重试条件，保持有限退避并返回准确重试提示。
   - 真实对象缺失或元信息不匹配：保持 404/拒绝，并修复素材持久化/对象生命周期链，不可改成放行。
   - SDK 错误分类问题：添加针对真实错误类型的测试后再修映射。
4. 调整失败语义：Worker 错误阶段/代码应该指向“参考图交付/素材暂不可用”，不是 `PROVIDER_UNAVAILABLE`。重试策略依照根因：瞬时错误可重试，配置错误/永久不匹配应停止并提示修复素材或配置。测试拒绝 malformed/oversized correlation header，确认 TaskSpec 不能注入/覆盖 ID，且同一请求在两端日志关联一致；另以恶意/超长 SDK `name/code/message` 测试日志仅出现安全枚举和受限状态码，不出现原始值。
5. API readiness 可考虑添加轻量对象存储依赖健康检查，但不把常驻 readiness 作为对象存在证明；明确是活性还是就绪检查，并评估 MinIO 故障是否会不必要地阻止与存储无关的项目 API。不得仅通过添加健康检查掩盖 503。

在根因仍未知时，允许完成只读证据收集与诊断日志/关联能力测试，但不得宣称“修复了本次失败”。

## 6. 测试矩阵

### 前端

1. 给定旧 Run FAILED + segment FAILED，点击总重试：同步清除旧错误视觉；显示“正在提交重试”；按钮被禁用；不要显示理解需求。
2. 给定同一数据，点击单段重试：页面反馈和 `ProductionProgressPanel` 一致进入 pending；不残留旧 safe_summary。
3. retry command 返回 202/成功响应：展示该新 attempt 的权威活动状态；延迟到达的旧 project refresh、旧 SSE/event 不回退 UI。
4. retry command 立即失败/超时：pending 退出并显示本次提交错误；不能误报后端已开始生成；旧 run 错误作为历史状态可在细节区查看，但不伪装成本次重试结果。
5. 新 attempt 后端再次 terminal FAILED：只展示新 attempt 的错误摘要，不复用旧 attempt 的 summary。
6. 两个重试入口共享同一状态 reducer/优先级；重复点击不重复发命令。

### API/存储/Worker

1. 有效签名 + READY 正确对象 metadata：HEAD 返回 200、内容为空、正确 MIME/长度。
2. 无效/过期签名、项目/资产/hash/MIME 绑定不匹配、真实对象不存在：保持 404；日志不泄露签名 token 或对象路径。
3. MinIO 连接超时/5xx：API 返回适当 503；错误被标为可恢复；有限重试/退避生效。
4. AccessDenied/桶初始化权限错误：不会对同一永久错误浪费三次重试；错误类型可诊断且安全。
5. HeadObject NotFound 和 AccessDenied 的 SDK 行为必须用当前实际 SDK 和 MinIO/Postgres 集成环境验证；不得凭错误文本猜测。
6. Worker 在 relay 503 时不创建 ProviderAttempt、不 POST Provider、不创建 usage/charge；保留当前 fail-closed 行为。
7. Worker/API correlation ID 精确匹配，日志可确定具体错误阶段；扫描日志确认无 query/token/URL/key/secret/prompt/原始 SDK 错误字符串。
8. 参考图 HEAD 恢复 200 后只跑 mock Provider 端到端，验证素材传输链；真实 Provider 单独授权后测试。

## 7. 验收标准

- UI：点击重试后立即不再呈现旧失败为当前状态；“提交中”和“已受理制作中”语义准确；新旧 attempt 响应不会串线；按钮及错误展示一致。
- 后端：对同类 503 有一条新的可复现/可关联底层原因证据链，不止是猜测；若历史 Run 因无 correlation 无法追溯，明确保留该限制；修复具有明确负例；参考图校验仍 fail closed。
- 正确错误类型和用户安全文案，不再把参考图交付失败归类成视频 Provider 故障。

## 11. 本地成功、VPS 失败的新增差异诊断（2026-10-13）

### 11.1 证据与因果假设

检查本机开发目录 `D:\AI\alchemy_video_OS\开发版_20261009` 后，发现其 Git HEAD 为 `071f46e0321300656972c48697e2703fe2ba736c`，工作区有 23 个修改/新增条目；本地审查 checkout 则是 `145099b6b67e969db0ea8bcb7039a85f8af84415`，有另一组未提交改动。两者不是同一源码快照，且部署/VPS当前 digest 尚未通过 SSH 只读核验。因此“本地成功”不能直接证明 VPS 与本机使用同一代码、镜像或配置。

- `infrastructure/deploy/README.md` 声明 app MinIO 身份是 least-privilege，特意不授予 `PutBucketCORS`；CORS 由固定 MinIO 服务级配置 `MINIO_API_CORS_ALLOW_ORIGIN` 管理。

将 CORS 配置视为基础设施职责，不允许运行时 app StoragePort 改写 bucket CORS：删除 storage client 的 `PutBucketCorsCommand` 初始化调用、与之仅相关的 `browserOrigins` runtime 配置及不再需要的 501 特判；保持 bucket 读取/创建和对象访问原有权限门禁不变。部署 MinIO 服务级 CORS 仍需覆盖 Studio 上传所需的 origin、`PUT`、`Content-Type`/`If-None-Match` 及 `ETag` expose；此次不能为了本地通过而扩大 app policy 权限。

加入负向回归：模拟 app identity 的 `HeadBucket` 与 `HeadObject` 成功、但对 `PutBucketCors` 返回 AccessDenied；修复后存储元数据读取必须成功，命令序列不得包含 `PutBucketCorsCommand`。同时覆盖缺桶创建路径，确保创建后不再要求 CORS 管理权限。另确认已有 deployment Compose 的服务级 CORS 设置与浏览器上传契约相符。
