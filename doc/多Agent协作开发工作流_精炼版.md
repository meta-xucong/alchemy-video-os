# 多 Agent 协作开发工作流（精炼版）

版本：1.0

适用范围：需要按开发文档、明确边界和实现约束开展的 AI 协作开发。采用三种职责、一张任务单、四步流程，重点保证改动不越界、验收有证据。

本方案融合用户讨论确认的协作机制及所提供的 Vibe Coding 行为原则。它是通用工作流说明，不替代项目开发文档，不自动改变项目规则、权限配置或章节验收状态。

## 1. 开发原则

| 原则 | 执行要求 |
| --- | --- |
| 查档求证，坦诚存疑 | 接口、业务规则先查代码、契约和文档；未验证的假设明确标注，不能冒充事实实施。 |
| 对齐需求，明确规则 | 开工前确定目标、范围和硬约束；已有依据与授权足够时直接执行，缺少关键业务选择时再询问。 |
| 复用存量，遵循规范，小步迭代 | 优先使用已有实现；按可审查的小批次修改，不夹带无关功能、重构或架构调整。 |
| 必要校验，证据验收 | 验证覆盖本次关键风险并满足项目规定；不无限扩测，不凭口头承诺或测试数量判定完成。 |

具体硬约束优先于笼统表述。例如，任务明确要求“不新增变量、不重命名”时，不能以“整体复用了旧代码”解释违反项。实现方式确实与目标冲突时，主控核实当前有效要求，记录冲突及最小调整建议；未经已有授权或用户明确调整，不得自行豁免。

## 2. 三种职责

| 职责 | 负责内容 | 边界 |
| --- | --- | --- |
| 主控 | 理解要求、确定范围、调研关键依据、拆分任务、协调依赖、整合交付。 | 不扩大需求、不降低验收标准；亲自修改的代码同样接受独立审查。 |
| 开发 | 在分配范围内实现、必要自测、提交差异与证据、修复审查问题。 | 不自行添加例外；额外优化只记为建议，不混入当前交付。 |
| 独立审查 | 检查需求偏差、范围、硬约束、代码正确性和验证证据。 | 对被审业务代码只读；自行核实关键事实，不凭作者自述放行，不以个人偏好追加需求。 |

默认使用主控、开发、审查三方；小任务由主控兼任开发，另一方独立复核。调研、测试、整合归入现有职责，不另设常驻岗位。只有任务能够独立实施、独立验收时，才增加并行开发者。

同一共享工作区内，一个文件同时只由一个负责人修改；共享服务、数据库和构建资源的变更操作同样指定负责人。独立工作区不自动隔离运行资源。审查员若参与业务修复，该改动需换另一方复核；工具支持时用权限或隔离落实只读边界。

## 3. 一张任务单

直接复用项目现有任务记录或章节模板，不另建平行账本。任务单提取要求并保留原文位置，不能改写或遗漏原约束；用户调整要求时，由主控统一更新并同步相关人员。

```text
目标：用户需要什么结果，怎样算完成。
范围：本次必做、禁做、暂不做及允许修改的文件或模块。
约束：逐项列出硬规则、原文位置和核查方法；无明确例外就不自设例外。
分工：开发负责人、独立审查人、必要依赖与共享资源归属。
版本：开发前实际基线（含已有未提交修改），待审查的最终差异。
验收：按第 5 节逐项填写证据、结论和剩余问题。
```

## 4. 四步执行

1. **定范围。** 主控读取相关文档和现有实现，检查工作区，形成任务单，审查方核对关键边界。先处理足以推翻方案的不确定性和规则冲突。跨模块任务先确定接口和依赖，再分配实施。
2. **按范围实施。** 开发者小步修改并自测，每组有意义的改动必须对应需求或必要配套工作。进入新模块、改变公共接口、引入依赖或可能突破硬约束前，立即检查范围。现有授权不足时，仅暂停有关部分并说明需要的决定。
3. **独立审查。** 开发者提交稳定版本与证据，审查方核对同一版本的差异、行为和约束。问题交回负责人修正；代码或证据变化后，复核受影响部分。开发中可以提前提示风险，不把尚未完成的中间状态反复当作最终审查失败。
4. **整合交付。** 主控整合改动，按风险验证最终组合的关键用户流程，确认交付版本与审查版本一致，再给出验收结论。接口接线、配置和运行产物受影响时，必须验证实际生效情况。

纠偏贯穿四步：**每项重要改动都要说明“对应哪条要求、为什么必要、是否新增行为”。** 文件在允许范围内，不代表可以在其中任意增加功能；未来规划也不等于当前授权。没有需求依据或必要性证明的改动不得进入交付。发现越界后，暂停有关改动并作最小修正，保留用户及其他任务已有修改。

## 5. 证据审查

审查最终全部差异，包括主控整合、测试修改及受影响的生成文件。机械检查适合验证声明、字段等明确约束；行为是否越界仍需对照需求审查。工具无法可靠检查的部分明确记录缺口，不能把一次搜索当作完整证明。

以下表格作为任务单的验收部分，按实际要求填写。示例中的变量或来源限制仅在任务明确要求时适用，不自动成为所有项目的禁令。

| 要求或约束 | 必须提供的核查证据 | 结论 |
| --- | --- | --- |
| 达到本次目标 | 用户行为或关键流程的验证结果，以及未覆盖部分。 | 待填写 |
| 不超出范围 | 需求与最终改动的对应关系；配套改动的必要性说明。 | 待填写 |
| 不新增或重命名变量（若要求） | 基线与最终版本的声明、名称和引用差异；适合时使用语法解析检查，核查可疑删除与新增。 | 待填写 |
| 按指定方式实现或复用（若要求） | 指定文档或来源版本、文件和符号，与最终实现或调用路径的对应；偏离依据及行为验证。 | 待填写 |
| 必要验证完成 | 对应最终版本的命令、环境和结果；失败、跳过及测试删除或改写的原因。 | 待填写 |

变量总数不变不能证明没有新增或重命名。不得通过动态字段等方式绕过约束原意。“已遵守”“已自查”“测试全绿”不能单独证明符合要求；修改断言、删除或跳过测试不能用来掩盖失败。

每项结论只允许：

- **符合**：在规定检查范围内，有足够证据证明满足要求。
- **不符合**：已发现具体违反项，须修正。
- **证据不足**：基线、检查覆盖、版本对应或关键验证缺失，须补证。

待填写、不符合、证据不足均不能放行。证据应可复查并脱敏；相关实现变化后，旧结论不能直接沿用。同模型的多方一致意见也不能替代证据。发生争议时，主控依据原始要求、同一版本差异及可复现结果组织复核，不凭多数意见或措辞强弱裁决。

## 6. 完成与效率

**通过条件：目标达到、范围符合、全部硬约束通过、必要验证完成，且证据对应最终交付版本。** 功能成功不能抵消违规；安全阻断可以是阶段成果，但不代表所需功能已完成。

为减少协调成本：

- 只并行真正独立的工作；依赖未满足时，不基于猜测提前实现。
- 子任务返回结论、证据位置、问题与下一步；完整日志保留在可检索记录中。
- 同一问题编号后持续更新，没有新证据不重复广播；范围、接口或分工变化由主控统一同步。
- 重复尝试没有新进展时，先查阻断、缩小复现或调整分工；更换执行者前确认旧写入操作已停止。
- 必要验证通过后结束任务；只因新增差异、失败、未决风险或项目要求扩大检查，不无理由重复全量测试。

交付说明包含修改内容、范围与硬约束审查结果、验证证据、未完成事项。若当前工具不支持独立审查，应如实保留该缺口，不将同一作者的自查称为独立审查。

项目已有更严格的来源复用、章节状态、测试或发布要求时，继续沿用；本方案不自行授予提交、推送、部署或外部调用权限。在本仓库使用时，任务单及证据并入现有章节执行和审计记录，沿用既有章节门禁，不另设一套状态机。
