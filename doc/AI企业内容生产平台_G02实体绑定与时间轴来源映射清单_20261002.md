## 限定推断与未授权偏离

1. 研发灌装与新加坡天际线是同一个设施内的镜头环境；设施窗外可见天际线是本轮获准的最窄构图推断。它必须与用户确认的原词义一致，不允许添加具体真实建筑、工厂品牌、认证、设备、城市地标或功效声明。用户明确确认三部分画面作为本次三段对照，故其第一/第二、第二/第三边界是两个获批编辑性场景切点；这也与 Huobao 强制 beat 切段相一致。平台通用规则不应把 NarrativeBeat 数量机械等同 TaskRun 数；但本任务经逐项 source mapping 明确为三个获批 beats 对应三个 Huobao 强制切段，因此恰为三段，既不能跨来源边界合并，也不能增段。profile 安全时长必须兼容三段 30 秒计划，否则 BLOCKED，不追加第四段。普通 entity/action/camera/shot 变化留在段内时间轴。
2. 新增实体的 `name/description/source evidence` 必须可回溯到当前批准的 Brief 或用户已确认的构图；女性只使用 Brief 已有的“约 25 岁东亚女性自然使用产品”描述，不增加五官、服装、品牌或可识别真人肖像。若已有 READY 素材无法支撑必需绑定，当前宽授权只允许生成最少的源内容参考图：一张女性自然将乳霜涂于面部、画面不出现罐/盒或其他可单独绑定实体；一张表现“白色高科技护肤研发/灌装空间、窗外新加坡城市天际线”的单一场景；不生成其他实体/镜头素材。所有图像仍必须经现有资产与 Brief revision 流程授权映射。当前三个已批准 asset ID/SHA 本身不证明新用途；未声明前不得映射。
3. 面霜罐与外盒分别作为关键 props；只在当前 segment 明确使用、展示或特写时绑定。用户未确认时不增加其他实体。
4. 对每个 segment 的来源引用做逐实体保真，而非仅检查总锚点数：镜头中出现女性时须有对应角色 `@` 引用及该 Brief revision 的精确 usage 映射；面霜罐/外盒分别按是否出现、使用或特写来绑定；任何明确 `@` 的场景也须有对应 usage 映射。精确结构和跨阶段校验按 TaskSpec §3.1.8；当前 v1.0.13 只接受同一冻结 Brief `source_asset_roles[].usage`，不接受 direct-image observation、metadata 或模型文本作为映射证据。Main 检查 bytes/SHA 是冲突否决门，不是证据生成入口；缺任一必需映射即 BLOCKED，不得让产品图替代人物引用。
5. 来源 `saveDedup*` 更新已有行，本平台设计要求 immutable revision。身份键保留来源精确规则：character/prop 使用 `normalizeName`（去成对括号内容；未闭合括号起截断；去空白/全角空格；lowercase）；scene 使用 `normalizeLocation`（只去空白/全角空格并 lowercase，不删括号）加 exact `time || ""`。平台不得增加 fuzzy match；一个 identity 一个逻辑 entity ID，以最大单调 revision number 为 current revision，append 需事务化且 `(entity_id, revision_number)` 唯一；冲突无法唯一确定时 fail-closed。匹配后按来源 truthy-fallback 合并字段，保持旧 name/location/time。hash 投影字段、初值与来源 merge 规则依 TaskSpec §3.1 第9项；实体摘要对固定字段数组直接调用 `semanticValueHash(fixedArray)`，helper 内部只 canonicalize/hash 一次；不得传入已序列化字符串造成二次 canonicalization，也不得另写序列化/hash 算法。ID、timestamps、evidence 和 asset bindings 排除。hash 相同复用 revision，变化追加 revision。该 hash/copy-on-write 机制是平台版本化适配，必须以来源 merge 行为的正反测试证明。

- 负例副作用：planning 失败时无新增 entity revision/READY storyboard/PromptPackage/成功 outbox；允许且断言既有流程的 Brief FAILED 与 `creative_brief.planning_failed` 失败 outbox。schedule 失败时无 Shot/reference binding/TaskRun/queued outbox；Worker 校验失败时无 ProviderAttempt/submit。
- 竞态正例/负例：两个并发顺序分别执行 ADD/REVOKE 与 `ensureProviderAttempt`。若 REVOKE 先提交，新的 Attempt 和 Provider submit 必须均为 0；若 Attempt 事务先提交，则该 Attempt 成为持久化提交意图并可继续，之后 REVOKE 仅阻止未来 Attempt。已有 provider request 仅 GET-only 恢复。
