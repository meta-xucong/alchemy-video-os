# C11.6 真实镜头分段与运镜稳定性开发设计

状态：`ACCEPTED`（2026-08-23 独立审计完成）

## 1. 目标与问题边界

现有 C11.3 已经产生 `MotionBeat`。此前 C11.6 错误地把“动作多或有运镜”直接提升为多个短 `GenerationSegment`，使一个 15 秒故事被强制拆为三段约 5 秒视频；每段都从相近的建立画面开始，反而造成场景重复和衔接风险。

本修订恢复正确的层级：`MotionBeat` 是同一视频中的时间轴，不等于 Provider 调用。只有超过已认证的单次时长上限、用户明确写出编辑性场景切换，或短内容出现足够强的语义编辑边界时，才创建额外 `GenerationSegment`。旧规划、旧 TaskRun、旧 PromptPackage 和公开 DTO 保持只读兼容，不被原地改写。

本增量只处理本地规划、Provider 输入快照、首尾状态和 Mock 验证，不执行真实 Provider、Veyra、VPS、SSH、DNS、部署、付费调用或 Git 写入。自动旁白不要求用户上传音频；用户授权的本机 Grok/Doubao 对照仅按最新自动音频执行文档单独运行，不改变本章范围。

## 2. 复用来源与适配边界

- `upstream/huobao-drama/backend/workspace/skills/storyboard-breaker/SKILL.md`：复用 2-4 个子镜头、动作/视角/道具/场景变化作为镜头边界的语义；不复制 Agent、数据库和进程内状态。
- `upstream/seedance-2.5/skill/seedance-25/references/long-video.md`、`prompting.md`、`editing.md`、`white-model-storyboard.md`：复用时间戳、单镜头主运动、起止状态、全局连续性锁、物理转场载体和首尾帧延续规则。
- `upstream/openmontage/lib/shot_prompt_builder.py`、`variation_checker.py`、`slideshow_risk.py`：复用景别/运镜词汇和“运动必须有镜头意图、不能全片静态”的 QC 语义；不复制 Backlot 或本地文件事实源。
- 现有 `packages/provider-video`：继续复用 `VideoProviderPort`、Sub2API 字段映射、提交/轮询/下载协议和 profile 能力边界，不把 MCP 编排搬入业务层。

## 3. 内部执行模型

规划链路固定为：`NarrativeBeat -> MotionBeat -> CameraShotSpec -> GenerationSegment`。`MotionBeat` 始终是片段内部时间轴；`CameraShotSpec` 给出该 Provider 片段的总体景别、方向与起止状态。动作和运镜节拍不会单独生成 Provider TaskRun。

`CameraShotSpec` 为内部规划类型，包含序号、时长、叙事目的、景别、角度、唯一主运镜、方向、起始状态、结束状态、转场说明和连续性锁。前端不接收这些工程字段。

## 4. 自动分段策略

系统按最少调用原则选择片段数，不让用户手工配置：

- 15 秒及以内：默认 1 段；简单单动作不强行加入时间戳。只有存在多个真实可见动作时，才按上游规则生成 2-4 个 `MotionBeat`，每个节拍只描述一个主动作，不补空节拍、不重复同一动作。
- 15 秒及以内且用户明确写出编辑性切换（如“镜头切换”“画面切至”“场景切换”“转场到”）：最多拆为 2 段，并在切换点建立依赖。
- 15 秒及以内且存在对白/情绪落点、特殊视觉变化或地点/时间变化时，使用受控语义切点评分；达到阈值且至少有两个动作阶段时最多拆为 2 段。普通“进入、观察、取物、交付”等连续动作不因动词数量自动拆段。
- 超过 15 秒：按 `ceil(目标时长 / 15)` 得到最少 Provider 片段，叙事点优先落在这些片段的自然边界。
- 道具换手、角色动作密集、运镜词、叙事点数量和“多镜头”描述都不能单独增加 Provider 调用次数。

因此，15 秒普通连续动作仍是一个 15 秒请求：它有一个总体主运镜和一个不重复的可见动作，不靠三次重新开场来制造镜头变化。对白、特殊视觉效果或空间/时间转折达到语义阈值时，才升级为多机位、多片段计划。多段时，每段仍只保存一个清晰总体镜头方向；相邻段依据已验收的结束状态继续，而不是复述前段已完成动作。

### 4.1 片段内部多机位覆盖（兼容说明）

旧版 v4 设计曾在一个 15 秒片段内按节拍自动补出“主运镜、侧向跟拍、中近景推近、环境反打停稳”等合成机位数组。独立审计后确认，这会把没有来源依据的镜头变化写进 Prompt，并与“一个可观察源动作对应一个主运镜”的 C12.6 修订冲突。当前实现保留编译器对**显式提供的**多机位时间轴的兼容能力，但确定性默认规划器不再因为节拍数量自动生成上述合成机位。

当前两层判断为：

- `GenerationSegment` 数量只由时长上限和明确的语义编辑边界决定；普通连续动作不因此增加 Provider 调用。
- 默认每个片段从源动作推导一个清晰的 `primaryMovement`。只有用户/上游输入已经声明了有序机位覆盖，或经过批准的私有运动时间轴明确包含多个不同机位时，编译器才要求 Provider 执行片段内多机位切换；平台不得凭 beat 序号臆造侧向跟拍、推近或反打。

编译器检测时间轴中是否存在多个机位。存在时，Prompt 明确要求上游执行“有序的片段内多机位切换”，并继续锁定人物、服装、场景、道具和动作方向；不存在时，仍要求一个清晰主运镜，避免短片段被无意义地拆动。该字段进入不可变 `input_snapshot.motion_timeline`，Worker 重启或重试不会重新编排。

这解决的是平台侧“有没有把**已声明**的多机位意图正确传给 Provider”的问题，不宣称上游模型必然严格执行。真实 Provider 仍需用新 TaskRun 验证成片；历史成片保留原 Prompt，不会自动重渲染。

## 5. Prompt 与 4096 字节边界

Prompt 按以下优先级编译并压缩：用户明确约束 > 角色/场景/道具连续性锁 > 对白与声音策略 > 景别/主运镜/方向 > 起止状态和动作终点 > 风格与次要修饰语。原文中明确出现的引号台词或说话语句会编译为私有 `Dialogue contract`，要求上游保留原语言人声、口型同步且不能用字幕或静音替代；当提示词超过 Sub2API 实测 4096 UTF-8 字节时，该对白契约与镜头/起止状态契约一并保留。Sub2API 实际 profile 的 4096 UTF-8 字节上限仍由 `VideoProviderRuntimeProfile` 约束；平台 20,000 字节预算不被恢复为前端硬拒绝。

压缩不得从字符串前缀直接截断掉镜头规格。冻结到 TaskRun 的 Prompt 和 `motion_timeline` 必须一致，Worker 重启不得重新规划或重复提交。

## 6. 首尾帧与转场

相邻片段依赖前一段通过技术 QC 后的尾帧。下一段以交接首帧优先，附带用户参考素材，并明确前段已经完成的动作不得重演。C12 继续负责边界评估：评估明确为 `PASS` 时直切；明确为 `BLEND` 或 `BRIDGE_REQUIRED` 时才按受控计划处理。评估器 `UNAVAILABLE` 或 `FAILED` 时只记录 `NEEDS_ATTENTION` 并直切，绝不伪造淡变修复。转场必须具备具体物理载体，不使用“平滑转场”空泛描述。

## 7. QC 与失败恢复

提交前检查：片段时间连续、每段只有一个主运镜、景别有变化、起止状态完整、参考图顺序和对象锁保持不变。生成后复用现有 ffprobe、首尾帧和 C12.1 评估边界；将 `MOVEMENT_PRESENT`、`STATIC_UNEXPECTED`、`SHOT_UNCLEAR` 作为内部结果。没有视觉评估能力时必须报告 `UNAVAILABLE`，不得伪造通过。静态异常只重试对应片段，并一次只调整一个镜头变量。

## 8. 兼容性与门禁

- 旧 `MotionPlan` 没有新字段时继续按原兼容路径解析；旧历史 TaskRun 不修改。
- 公开 OpenAPI、AsyncAPI、SSE 和 Studio DTO 不增加 CameraShotSpec、Provider 字段或 Prompt 原文。
- 规划、PromptPackage、TaskRun 快照和生产片段数量必须一致；15 秒高复杂度 Mock 夹具必须只产生 1 个真实生成片段，30 秒/18 叙事点夹具默认产生 2 个 15 秒片段。
- 必测：规划分段、语义切点评分（特殊视觉效果/对白/场景时间变化与普通连续动作对照）、单主运镜、时间轴连续性、4096 压缩保留镜头规格、交接依赖、Worker 不重复提交、最终音轨/时长/成片版本。

实现顺序：先更新内部类型和规划器，再更新 Prompt 编译/压缩，再补生产快照与 Mock E2E，最后独立审计。真实 Provider 验证另行授权，不属于 C11.6。
