> 本文是《AI企业内容生产平台_原仓库原则驱动的4096UTF8保真保护性压缩开发文档》的受控增量。它只增加“提示词预算预检失败后，复用现有智能分段按同一规则递增重规划”的协调行为；不替换原压缩规则，也不改变公共契约、任务状态或 Provider 协议。

## 1. 用户目标与问题边界

用户希望：当现有智能规划得到的某个生成片段在 Provider 的 4096 UTF-8 字节预检中无法通过时，程序继续复用同一套语义分段规则增加一个生成片段并重新编译提示词，直到所有片段通过或已有时长边界无法再表达；成功则继续制作，仍无法通过则明确阻断。

当前行为是：Workflow Worker 完成 `StoryboardPlan -> PromptPackage` 后才由 Production Worker 的 runtime-profile 做 4096 预检。若源内容或保留的必要内容无法安全压缩，任务在 Provider 提交前以 `PROMPT_BUDGET` 阻断；现有 planner 不读取提示词字节预算，因此不会再次规划。

本方案只处理新规划尚未落库/尚未创建 Provider TaskRun 的阶段。已经创建的不可变 `TaskRun.input_snapshot` 不原地修改；已经提交 Provider 的任务不回溯拆分、不重复提交、不重复扣费。

## 3. 冻结的最小流程

### 3.1 第一次规划与预检

1. Workflow Worker 按现有 `PlanningModelPort.plan` 生成计划。
2. 按现有 `DeterministicStoryboardCompiler` 编译每个 `PromptPackage`，保留现有 `source_prompt` 与 `generated_prompt_parts` 私有 sidecar。
3. 仅当当前 runtime profile 明确是 `sub2api` 且有既有有效 Provider prompt ceiling 时，使用 `compactRuntimePrompt` 对每个编译结果做同一预算预检：
   - 已在 ceiling 内：原样通过，不触发重规划；
   - 可依据 sidecar 省略派生块或既有白名单后通过：原样通过，不触发重规划；
   - 以既有 `UnsupportedVideoGenerationInputError` 且 `code === "PROMPT_BUDGET"` 失败：进入递增重规划；
   - 其它错误：沿用原错误，不转换为重规划。
4. 所有片段预检通过后，才执行现有 `completeCreativePlan` 持久化和后续 outbox/队列流程。

Mock/缺少 Provider capability 的规划不触发该重规划；默认 Mock 仍按本地规则工作。

### 3.2 递增语义重规划

1. 仅在预检返回既有 `UnsupportedVideoGenerationInputError` 且 `code === "PROMPT_BUDGET"` 时继续；每轮把当前结果的 `generationSegmentCount + 1` 作为内部 `minimumGenerationSegmentCount`，再次调用同一个现有 planner。该字段只存在于 `PlanningInput` 内部类型，不进入公开 HTTP、数据库 schema、事件或浏览器 DTO。
2. 以现有 `durationPolicy.minDurationSeconds` 和 brief 的 `targetDurationSeconds` 推导可表达的最大段数；没有有效时长策略、下一段数超过该边界，或 planner 返回的段数没有严格增加时，沿用原 `PROMPT_BUDGET` 阻断，不猜测固定次数、不循环等待。
3. `chooseGenerationSegmentCount` 每轮先执行原有目标时长、场景、叙事点和口播容量规则，再取不小于 `minimumGenerationSegmentCount` 的结果；最终仍由既有 domain/persistence storyboard invariant 校验合法时长和顺序。
4. 每轮重规划必须重新分配：
   - `NarrativeBeat`/`MotionBeat` 到每个独立片段；
   - 每段口播行和段落边界；
   - 每段时长、开始/结束状态和依赖；
   - 现有 `REFERENCE_SET`、`HANDOFF_FIRST_FRAME`、`TEXT_TRANSITION` 策略。
5. 重新编译所有片段并再次执行同一 `compactRuntimePrompt` 预检；循环只在上述预算错误且仍有可表达的下一段时继续：
   - 全部通过：只持久化最后一次完整规划；
   - 任一片段仍返回 `PROMPT_BUDGET`：继续下一轮，直到边界；
   - 达到边界或 planner 无进展：沿用既有预算阻断；
   - 出现其它规划/契约错误：沿用原错误，不重规划。

### 3.3 时长和语义约束

- 不固定为 7.5 秒；时长由现有 `durationPolicy` 和 `planSegmentDurations` 分配。Grok 的 `1..15` 与默认 Huobao 的 `8..15` 仍按已解析 profile 决定，不能互相冒充。
- 不按字符、字数、浏览器行数或字节位置切源；只使用已有段落、标点、场景、动作结束姿态和口播容量边界。
- 一个不可再分的源单元即使超过预算也必须保持完整并最终阻断，不能为了凑字节截断。
- 不把完整原提示词复制到每个新片段；每个片段只带自己拥有的 source、dialogue、motion 和引用事实。全局锁按现有编译器规则保留必要内容。

## 4. 不变量与安全边界

- **Provider/计费边界**：所有递增规划和预算预检都发生在 `completeCreativePlan` 之前；没有 Provider submit、轮询、下载、媒体 Runtime 或扣费副作用。
- **不可变性**：第一次失败的未持久化草稿不产生正式 revision；已有 revision/TaskRun 不被覆盖。后续用户重试通过既有新 revision/新运行路径处理。
- **幂等性**：Workflow 事件仍使用既有 command/event 幂等；一次执行仅在预算失败时按已有时长边界递增调用 `plan`，重启后的事件回放不创建第二个 revision。
- **来源 sidecar**：预算预检只消费已存在的 `capabilitySnapshot` sidecar；缺失或不匹配沿用 `PROMPT_BUDGET` fail-closed，不按字符串猜 provenance。
- **模块边界**：不修改 `packages/provider-video/src/runtime-profile.ts`、公开 contracts、DB schema、任务状态、Billing、Provider adapter、Studio API、VPS 或 Sub2API。

## 6. 行为测试与验收标准

### 6.1 必测场景

1. `sub2api` 初次所有片段预检通过：planner 调用一次，计划和 prompt sidecar 与现有结果一致。
2. 某片段初次返回 `PROMPT_BUDGET`、前几次增加一个语义片段后仍超限、最终一次通过：planner 按 `2→3→4→5` 递增调用；每段 source/dialogue 顺序完整、UTF-8 字节数不超过 4096；最终只持久化最后一次 draft。
3. 达到 `targetDuration/minDuration` 边界、planner 无进展或没有 duration policy 仍超限：抛出 `PROMPT_BUDGET`，不调用 `completeCreativePlan`，不产生 outbox/Provider/Billing，且不会无限循环。
4. 初次错误不是 `PROMPT_BUDGET`：不重规划，原错误类型/消息沿用。
5. 缺 sidecar、sidecar 不匹配或不可表达源单元：只允许既有 fail-closed，不静默截断/重排。
6. Mock/未知 profile：不触发预算重规划；默认行为和现有测试保持。
7. 口播多行、中文 UTF-8、中文/ASCII 引号、`@anchor`、参考图顺序和 motion beat 归属在重规划后保持。
8. 默认 `8..15` 和已认证 Grok `1..15` 的合法时长由同一 `durationPolicy` 校验；不可形成合法段时沿用 `STORYBOARD_SPEC_INVALID`，不补长、不慢放、不造 7.5 秒硬阈值。
9. 一个不可分源单元超过 4096：递增重规划直到已有时长边界后仍阻断，不能按字符切开。

## 7. 已知限制

- 三个固定上游没有“4096 超限后自动重规划”的通用算法；本功能是平台在既有来源分段规则之上的内部协调薄壳，不能宣称原仓库原样提供。
- 递增段数不能保证极端长 source 一定可表达；达到已有时长边界或 planner 无进展时阻断是预期结果。
- 本方案只覆盖 Workflow 新规划路径；已有运行的恢复、已提交 Provider 的重试和历史快照不被改写。
- 字节预检成功不等于真实 Provider、音画或人工质量验收通过；真实调用和产物审核仍按既有授权/审计门禁执行。
