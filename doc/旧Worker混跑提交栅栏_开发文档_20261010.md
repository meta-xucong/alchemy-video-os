## 1. 目标与保证边界

`0027_provider_submission_reservation.sql` 新增 `submission_reserved_at`，新 Worker 先预留后 POST；但旧 Worker 不读该字段，新增列本身无法阻止旧代码继续提交。

本次在 `0027` 之后新增 `0028` 迁移，将 `provider_attempts.provider_request_id` 的数据库物理名称改为 `provider_request_id_v2`。新版本继续用逻辑属性 `providerRequestId` 访问它。旧版本查询原物理列时由 PostgreSQL 拒绝，阻止尚未通过 `ensureProviderAttempt` 的旧执行到达视频生成 POST。

**可保证的窄边界**：当 `0028` 已成功提交、数据库中不存在原列或兼容别名，且旧执行此后才进入 `ensureProviderAttempt` 的原列查询时，已核对的旧路径会在视频提交前失败，不会由这次执行发出新的生成 POST。此保证依赖旧二进制确实走已核对的数据库和代码路径；其他历史版本必须另行盘点验证。

该迁移不会撤销已通过门禁的执行，也不会取消已被上游接受的请求。它不提供全局停机、网络出口封禁、扣费封禁或零停机滚动升级保证。停流、排空、未知结果对账和全体 schema 消费者协调升级仍为上线前置条件。

## 3. 迁移与代码设计

### 3.1 物理列更名

`0028` 的核心语句为：

```sql
ALTER TABLE "provider_attempts"
RENAME COLUMN "provider_request_id" TO "provider_request_id_v2";
```

- 新建增量迁移及匹配的 journal/snapshot，不重写已发布的 `0027`。
- Drizzle 映射改为 `providerRequestId: text("provider_request_id_v2")`。现有仓储通过此属性读取、更新和构造索引。
- 更名保留每行已有值、NULL、类型及关联约束；须用真实隔离 PostgreSQL 验证值和索引，不仅检查 SQL 文本。
- 不新增原列、双写列、视图别名、触发器兼容层或旧列回退查询；这些措施可能重新放开旧 Worker 的提交路径。
- 不改变 `submission_reserved_at`。升级历史无 request ID 的 Attempt 仍先由 `0027` 保守回填预留，不能因本次更名推断其从未提交。
- DDL 的锁等待只覆盖相关数据库操作；此前已经返回的 `ensureProviderAttempt` 和事务外 POST 不会被该锁追溯阻止。

### 3.2 逻辑与外部契约保持

以下命名及行为保持：

- TypeScript `providerRequestId`、`ControlProviderAttempt`、`VideoProviderPort` 和仓储方法参数。
- 内部事件中的逻辑字段 `provider_request_id`，以及现有上游 `request_id` 映射。它们不是数据库列名，不应全局替换为 `_v2`。
- 公开 DTO/SSE 的现有脱敏边界，不向公开接口新增任一 request ID 字段。
- 已知 request ID 的查询、下载及恢复语义；未知结果的预留、显式重试和制作段重试阻断语义。
- `provider_attempts` 现有 Provider/request ID 唯一性及 NULL 语义。

契约文档应明确区分逻辑名与物理名，避免维护人员按旧名写直接 SQL。检查所有手写 SQL、测试夹具、诊断脚本及构建产物；仅靠更新 TypeScript schema 不能证明运行中的消费者已经兼容。

## 4. 旧 Worker 失败后的实际表现

### 4.1 迁移后才进入门禁

旧 `ensureProviderAttempt` 查询缺失列，PostgreSQL 返回 `42703`。旧 `providerStageError` 对这类普通异常归一为 `PROVIDER_UNAVAILABLE/retryable=true`，执行器抛出 `RetryableTaskExecutionError`，由 BullMQ 重试。栅栏不保证错误被旧应用干净地收敛为可见的 `FAILED`。

旧 `finalizeTaskRunExecutionFailure` 也读取原列。重试耗尽时收敛事务可能失败，TaskRun 因而仍为 `RUNNING`。旧队列适配器 `packages/task-queue/src/index.ts` 的 `createBullMqInternalEventWorker` 并行执行终态回调和 Redis DLQ 入队，所以在 Redis 入队成功的情况下可以出现“数据库仍 RUNNING、Redis 已有 DLQ”；不能把 DLQ 当作数据库终态证明。`apps/task-worker/src/index.ts` 内终态回调先收敛再释放消费账本，前者失败还可能阻止后者。

启动恢复同样不保证自愈：旧 `recoverC06TaskRuns` 等待 `finalizeFailure`，该操作再次因缺列失败时会向外抛出。入口在恢复完成后才 `worker.start()`，因此旧进程可能在启动阶段失败。现场不能仅靠重启旧 Worker 或反复消费 DLQ 处理。

### 4.2 迁移前已经通过门禁

可能时序：

1. 旧 Worker 完成 `ensureProviderAttempt` 并提交该数据库事务。
2. `0028` 提交列更名。
3. 旧 Worker 发出视频 POST，或更早发出的 POST 此时才被上游接受/返回。
4. 旧 `recordProviderSubmission` 因仍查询原列失败，本地没有保存已接受的 request ID。

这是需要对账的未知提交结果。即使停止进程，也不能撤回已被上游接受的请求。旧 transport 没有应用层显式 POST 超时/取消边界；仅“等若干秒”“lease 过期”或“队列无 active”不能证明该窗口已经消失。新版本的预留防重提也不能自动找回该 request ID。

### 4.3 其它网络与扣费路径

旧 `resolveVisualInput` 在 `ensureProviderAttempt` 之前执行，参考图交付会做 HEAD，并可能回退 GET；这些请求可先于列栅栏发生。已有状态查询、下载、对象存储及其它独立执行器不属于本栅栏的出口控制范围。

旧 `execute` 的 `BILLING_PENDING` 恢复分支在视频门禁之前，固定价格扣费路径可不经此次列查询；其它正在运行的扣费执行同样不受列更名取消。需要停止这些活动时，必须使用独立且已授权的运行控制方案，不能把物理列改名当作扣费开关。

## 6. 部署前切换清单（未执行）

以下是条件与核验项，不是可直接执行的生产命令。实际环境的停止、备份、迁移、重启和对账方式需由获授权的操作者依据已核实的运行配置制定。

1. **盘点版本和所有入口。** 记录 API、各 Worker、调度器、恢复进程、手工脚本的实际构建 SHA、数据库和队列目标；检查自动重启、扩缩容、旧镜像回滚及其它主机，不能只盘点当前终端进程。
2. **暂停新增流量与调度。** 暂停创建/重试提交入口及会派生任务的调度/relay；阻止旧 Worker 领取新任务。保存 queued、active、delayed、failed/DLQ 和未发布 outbox 的基线，不靠删队列“清空”事实。
3. **排查所有在途与未知提交。** 对照 TaskRun、Attempt、旧进程当前活动、上游请求/用量事实，区分未提交、已知 ID、结果未知及扣费中任务。旧版本无 ID 并不等于从未 POST。仅固定等待不能通过本门。
4. **先消除在途竞态并核对未知结果。** 在迁移/恢复前建立证据，确认无旧进程仍可能从已通过的门禁继续 POST；已接受请求按上游事实对账。无法取得可靠结论的未知项保持隔离和 HOLD，不重放 DLQ、不清预留、不新建替代 TaskRun。任何需要修改持久化事实的人工处置须另有审计依据和授权。
5. **验证停止与备份。** 核实旧消费者已停止且不会自动重启，备份相关数据库并确认可恢复方案；保留队列、outbox 和在途对账清单。备份并不能撤销外部已接受请求。

## 7. 停止恢复与回滚边界

出现任一情况立即保持或恢复停流，并由获授权操作者处理：发现旧构建/旧列查询；迁移值或索引不一致；无法对账的 POST/扣费；出现重复提交；未知任务被重试；恢复路径异常；RUNNING、DLQ、outbox 的事实不一致。

- 优先回到仍兼容 `provider_request_id_v2` 且保留提交预留保护的应用构建。旧 `071f46e` 或 `44da842` 原构建不符合此条件。
- **只要旧 Worker 仍可能运行、重启或恢复，禁止为“修复兼容性”恢复原列名、增加原列/别名或启用旧列双写。** 这会重新打开旧提交门，尤其会使未知结果重新面对重复 POST 风险。
- 数据库反向更名或备份恢复不是普通应用回滚。必须有独立受控计划：保持停流、确认全部相关进程停止、核对外部已接受请求与扣费、保留预留与 request ID 事实，并重新完成消费者/schema 对齐和恢复门。本文不提供自动 down migration 或生产回滚命令。
- 即使数据库恢复到旧快照，上游请求和费用也不会随之恢复；不得把旧快照中的“无 ID”当作再次 submit 的授权。

## 11. 已知请求 ID 的拒绝错误重试复审

同轮扩大到相邻防重路径的审计复现：当前代码把任意 `PROVIDER_REJECTED` 当作远端任务不存在，显式重试会放弃已有 request ID；HTTP 401/403/404 或 Worker 模型不匹配都可触发第二次 POST。离线 Mock 的实际方法序列为 `POST, GET, POST, GET`，说明提交预留本身不足以封闭显式放弃路径。

最小修复沿用固定基线 `a4cd33d` 中 `packages/provider-video/src/sub2api/adapter.ts` 的 `rejectedStates` 与 `errors.ts` 的 HTTP/状态两类归一化入口，区分“查询失败”和“已明确收到远端任务终态”。只允许成功状态响应中的既有终态分类提供内部证据；HTTP 404 也可能来自权限或路由，不能单凭它允许新提交。未知历史记录和通用错误保持已知 ID，优先恢复查询，无法核实时等待有依据的人工处理。详见同轮更新的《领域模型与 API 事件契约》ProviderStatus 段落。

该修复必须同时覆盖内存仓储、PostgreSQL 仓储、制作段新 TaskRun 重试及底层提交预留，不能只修 API 的一个入口。固定旧 Worker 夹具保持不变，仍只证明旧版迁移栅栏；新版本重试修复由单独 Mock/数据库回归提供证据。

内部字段为 `ProviderStatus.providerRequestTerminal?: true` 与 Attempt 私有 JSON 中的 `provider_request_terminal`。只接受严格布尔 `true`；SQL 与 JavaScript 对字符串、数字、数组、NULL 等值一致拒绝。历史 `ABANDONED` 已知 ID 没有可信终态证据时仍作为提交边界。不会自动给旧数据补写证据，也不会把已发生的重复请求视为已撤销。

制作段重试必须与普通任务重试使用同一 TaskRun 事务锁，并拒绝已进入 QUEUED/RUNNING 等活动状态的旧任务；后续 QC 失败的重新生成仍需持久化成功任务、成功 Attempt 与归属匹配的 READY 视频资产。以下为 `3fd8410` 基线的历史边界：已证实旧请求终结之后，制作段创建新 TaskRun，再由用户另行重试历史 TaskRun，仍可能重新激活旧任务；该基线不保证两种命令全面互斥。

2026-10-10 后续修订已按 [恢复一致性设计](closure-20261010/recovery-design.md) 实施私有持久替代关系及 `0029` 增量迁移，当前处于回归与交叉审计阶段，最终证据以 [实施与审计记录](closure-20261010/review-record.md) 为准，不能继承本节旧提交的 CI 结果。正常恢复命令只能操作尚未被取代的任务；不提供任意新生成命令的全局去重。历史 NULL 关系不证明从未发生替代，必须先对不明任务隔离对账。`3fd8410` 及更旧写入者不理解该关系，不能作为新迁移后的兼容回滚版本；全部相关写入进程的切换和回滚要求见 [验收及切换方案](closure-20261010/acceptance-and-cutover.md)。

若历史库同一 TaskRun 同时包含已知 ID 和另一条无 ID 预留，既有 GET/下载恢复可继续，但无 ID 预留不会被清空，仍阻止再次提交和重新生成。取得一个已知结果不证明其它历史未知提交已对账；生产切换须逐 Attempt 核对。
